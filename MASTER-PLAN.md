## Главный принцип заказчика

Приложение должно быть **автономным**: само берёт расписание, само парсит, само всё рассматривает.
Сервера у нас нет — есть только клиент. Конкуренты (ребята из колледжа) вайпкодят хуже по дизайну и
функционалу — мы на голову впереди, но **ошибок допускать нельзя**.
Всё должно быть: **быстро, оптимизировано, красиво, удобно**. Психология и физиология восприятия —
на первом месте (пользование одной рукой, подсознательная навигация, фидбэк на каждое действие).

- **Поиск по ключевым словам**: НЕ строгий (буква-в-букву люди ненавидят). Нужен популярный алгоритм
  нечёткого поиска, терпимый к опечаткам/грамматическим ошибкам + фильтр регистра + поиск по выражениям.
  Легко войти/выйти из режима поиска, удобная навигация по совпадениям.
- Много устройств, мало места в APK, эффективно и оптимизировано.
- _Решение (ponytail — native/stdlib прежде всего)_: **PDF → `android.graphics.pdf.PdfRenderer`**
  (встроен в Android API 21+, ноль зависимостей, рендер страницы в bitmap). **DOCX → собственный
  экстрактор**: docx это ZIP с `word/document.xml` — `ZipInputStream` + XML-парсер из stdlib дают
  текст с базовой разметкой (абзацы/заголовки/жирный) без тяжёлой зависимости (Apache POI/docx4j = +5 МБ).
  **Изображения → Coil** (уже в зависимостях). **Нечёткий поиск → SQLite FTS4 (Room @Fts4) + префиксное
  сопоставление**, плюс fallback с расстоянием Левенштейна/Даммерау-Левенштейна ≤2 для опечаток
  (проверить, что даёт лучший UX при малой цене). XLSX — по остаточному принципу (тоже zip+xml:
  `xl/sharedStrings.xml` + `xl/worksheets/sheet1.xml`), либо «открыть внешним».

**Просмотрщик изображений**:
- Поворот на 90° по кнопке; поворот **сохраняется** для этого изображения (следующее открытие — в нём же).

## 4.2 Оценки (крупная подфаза)
- **Список предметов** специальности/курса (из `MpkCurriculum`), справа у каждого — **средний балл**.
- Тап по предмету → экран оценок: по центру крупно средний балл, внизу **кнопки 1–10** — тап добавляет
  оценку в текущую категорию. Как в обычных андроид-приложениях для суммирования оценок: настройки,
  округление — перенять лучшее.
- **Категории оценок**: обычные (ответы на уроках/тесты), практические работы, контрольные работы,
  лабораторные (**зачёт/незачёт, не баллы**), экзамен (одна оценка: ввести/стереть/переписать).
  Обычных/практических/контрольных может быть несколько.
- Переключение между категориями при вводе.
- **Локальное хранение с датой** и подписью («какая именно практическая») → видно, какая работа
  не сдана (есть 1, 2, 4 → значит 3-я не сдана), и какие оценки когда выставлены.
- **Настраиваемое дерево агрегации**: пользователь сам решает, как считается средний балл.
  Режим редактирования приоритета групп — **перетаскиванием** менять порядок категорий; от порядка
  зависит сворачивание (может быть в формате дерева). UX должен быть понятен без инструкции.
- **Формула по умолчанию** (задал заказчик): парное сворачивание в порядке приоритета
  `[обычные, практические, контрольные, экзамен]`:
  1. `s1 = (avg(обычные) + avg(практические)) / 2`
  2. `s2 = (s1 + avg(контрольные)) / 2` — если контрольных нет, уровень пропускается: `s2 = s1`
  3. `итог = (s2 + экзамен) / 2` — если экзамена нет: `итог = s2`
  Категории без оценок **не участвуют**. Лабораторные — зачёт/незачёт, в балл не входят.
- Не отходить от стиля колледжа/приложения.

  ((обычные+практ)/2 + контр)/2 + экзамен)/2 с пропусками пустых.


До этой сверки исходить из худшего сценария: «файл доступен из вершины как минимум одной публичной ветки».

## 2. Оценка: кто видит и что уже утекло

### 2.1 Кто мог получить доступ (без выполнения атак)

| Вектор | Комментарий |
|---|---|
| `git clone` / `git fetch` | Публичный репозиторий клонируется **анонимно, без аккаунта**; нужен только номер коммита (`0d1d389`) — он виден в UI и в API |
| GitHub UI / blob view | Файл открывается в веб-интерфейсе по коммиту/пути, пока объект достижим из какой-либо ветки или по SHA |
| `raw.githubusercontent.com` | Прямые ссылки на файл по коммиту/ветке; могут кэшироваться CDN |
| Форки | Форк получает **всю историю на момент форка** и не обновляется при переписи в upstream; удаление в upstream форк не чистит |
| Боты-сканеры ПДн/секретов | Публичные коммиты массово индексируются сервисами поиска секретов и исследовательскими датасетами; факт появления файла в публичном коммите почти наверняка зафиксирован сторонними системами |
| GH Archive / BigQuery | События публичных репозиториев архивируются; содержимое файлов публичных репо попадает в исследовательские датасеты (выборка — нельзя исключить попадание). Из таких архивов удаление невозможно |
| Поисковые кэши | Страницы blob view могли быть проиндексированы |

## 4. Варианты ремедиации

### Вариант A — private + rewrite истории + force-push + форки/кэши (рекомендуемый)

**Суть:** сразу закрыть доступ (private), затем вычистить файл из всех коммитов/веток/тегов, force-push, добить кэши GitHub и форки, включить гейты.

- **Плюсы:** полностью убирает файл из официального репозитория; сохраняет issues/PR/историю проекта (с новыми SHA); стандартный путь, документирован GitHub.
- **Минусы/риски:** меняются SHA всех потомков `0d1d389` → ломаются чужие клоны, открытые PR, ссылки на коммиты; нужен freeze и предупреждение соавторов; форки не чистятся автоматически; кэши чистит только Support.
- **Когда выбирать:** если репозиторий нужен как рабочий (обычный случай), соавторов немного.
- **Время:** 2–4 часа + 1–3 дня на Support/форки/уведомления.

### Вариант B — удалить репозиторий / пересоздать в новой организации с чистой историей

**Суть:** заархивировать старый репозиторий (офлайн, зашифровано), создать новый (private) с чистой историей из текущего состояния (squash/orphan-коммит), переключить CI/remote/ссылки.

- **Плюсы:** гарантированно нет старых объектов и старых кэшей в новом репо; проще, если история «грязная» не только этим файлом (проверить `.env`, `*.jks`, `teachers.csv` с телефонами, старые admin-APK в релизах).
- **Минусы:** теряются issues/PR/Actions/звёзды/ссылки; старый репозиторий и его форки всё равно нужно удалять/чистить (форки после удаления upstream могут остаться самостоятельными копиями); выше риск потерять незапушенные 338 коммитов — их надо переносить патчами/через переписанную ветку.
- **Когда выбирать:** если история содержит другие ПДн/секреты или репозиторий можно «перезапустить» без потерь.
- **Время:** 3–6 часов + уведомления.

### Вариант C — оставить как есть, удалить файл новым коммитом, «ротировать» и уведомить

**Почему недостаточно (не рекомендуется как основной):**

1. **История остаётся публичной.** После `6affb7d` файл по-прежнему достаётся из `0d1d389` и потомков: `git fetch origin 0d1d389 && git show 0d1d389:app/src/admin/assets/students.csv`.
2. **Клоны/форки/архивы** уже содержат файл; их нельзя отозвать.
3. **Кэши GitHub** (blob view, raw CDN) живут независимо от новых коммитов.
4. **Внешние архивы** (GH Archive/исследовательские датасеты, сканеры) — неудаляемы.
5. **«Ротация» неприменима:** ПДн (ФИО, группа) нельзя «перевыпустить», как пароль. Ротация имеет смысл только для секретов (TOTP, PAT) — это отдельные задачи.
6. **Юридически** это сокрытие, а не устранение: уведомление всё равно потребуется, а доступность данных сохраняется.

**Допустимо только** как временная мера на минуты: «сделать private» (это и есть первый шаг A), пока готовится полная перепись. Вариант C в чистом виде оставляет инцидент открытым.

## 5. Точные шаги (вариант A) с проверками

> Все команды — **примеры для выполнения человеком с правами администратора репозитория**. В рамках аудита они не выполнялись. ПДн в вывод не печатать: только SHA, пути, коды ответов.

### Шаг 0. Freeze + evidence (15 минут)

```bash
mkdir -p evidence && cd evidence

# 0.1 состояние remote — по сети, а не по локальным refs
git ls-remote --heads --tags https://github.com/F-708/MPK-app-2.0 > remote-refs-before.txt
gh api repos/F-708/MPK-app-2.0 \
  --jq '{private,visibility,pushed_at,default_branch,fork,forks_count}' > repo-before.json

# 0.2 все коммиты, трогавшие файл (по GitHub API — не зависит от локального клона)
gh api "repos/F-708/MPK-app-2.0/commits?path=app/src/admin/assets/students.csv&per_page=100" \
  --jq '.[] | {sha: .sha, date: .commit.author.date}' > pii-commits.txt
wc -l pii-commits.txt        # ожидаем >= 1 (0d1d389)

# 0.3 зафиксировать хеш blob'а (без копирования содержимого)
```

### Шаг 2. Зеркало + перепись истории (1–2 часа)


## 10. Приложение: почему это вообще случилось (root cause, для пост-мортема)

- Файл с ПДн коммитился в репозиторий **до** появления `.gitignore` (коммиты `0d1d389`, `cb3bb1f` и др.).
- Позже файл убрали из индекса (`6affb7d`, «PII из индекса»), но:
  - **не переписали историю**;
  - **не запушили** удаление (локальная ветка впереди remote на 338 коммитов);
  - репозиторий при этом оставался **публичным**.
- Гейт «в стандартном APK нет `students.csv`» существует как ручная команда, но **не автоматизирован** и ничего не проверяет в git-истории.
- Синхронизация с публичным репозиторием описана как «скопировать main-репозиторий» (`RELEASE.md:45-46`) — при копировании дерева игнорируемые файлы (ПДн, ключи) уезжают вместе с кодом.

**Профилактика (после инцидента):** pre-commit hook + CI-гейт на `git ls-files`/историю, secret-scanning, синхронизация только через git, и правило «ПДн не попадают в репозиторий вообще — даже в admin-флейвор» (см. `security.md`, P0-2).

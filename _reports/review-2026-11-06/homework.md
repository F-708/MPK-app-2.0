## TL;DR

**Root cause одной фразой:** задание привязывается к уроку через **одну конкретную календарную дату**, а не к предмету-интервалу — `HomeworkMarkers.resolveNextOccurrenceIso()` (`HomeworkMarkers.kt:101-120`) возвращает **единственный** iso-день, и `markerLessonTypes` рисует бейдж только там, где `sameIsoDay(targetIso, day.dayIso)` (`HomeworkMarkers.kt:53-58`); все прочие вхождения того же предмета в расписании (другой день недели / другая пара) никогда не совпадают с этим единственным днём.

**Гипотеза №1 из брифа (бейдж горит только на первом вхождении, потому что `resolveNextOccurrenceIso` возвращает один iso-день) — ПОДТВЕРЖДЕНА** полностью, включая цепочку вызовов и точное место. Но это не единственная причина: дедлайн-ветка (`HomeworkMarkers.kt:53-54`) имеет ту же одно-дневную семантику, **а дедлайн вообще невозможно выставить из UI** (`TasksScreen.kt:1086`: `val dueIso = task?.deadlineDate ?: ""` — контрола ввода даты в диалоге нет). То есть **все без исключения** задания, созданные пользователем, попадают в одно-дневную ветку.

## Ответы на вопросы брифа

### 1. Как задание привязывается к уроку?

**Ответ: по `subjectName` + одна календарная дата.** Развилки ровно две (`HomeworkMarkers.kt:50-58`):

```kotlin
val matches =
    if (!subjectsMatch(subject, task.subjectName)) {
        false
    } else if (deadline.isNotBlank()) {
        sameIsoDay(deadline, day.dayIso)                 // :53-54
    } else {
        val targetIso = resolveNextOccurrenceIso(          // :56
            task.createdAt, subject, weeklyLessonsByDow)
        targetIso != null && sameIsoDay(targetIso, day.dayIso)  // :57
    }
```

`resolveNextOccurrenceIso` (`:101-120`) действительно возвращает **один** `String?` — первый день в 28-дневном окне от `createdAt`, где у предмета есть урок, чьё *время окончания* ещё не наступило на момент создания:

```kotlin
for (offset in 0 until 28) {                                  // :107
    val cal = (created.clone() as Calendar).apply { add(DAY_OF_YEAR, offset) }
    val dayLessons = weeklyLessonsByDow[Dow.of(cal)] ?: continue
    for (lesson in dayLessons.filter { subjectsMatch(it.officialSubjectName, subject) }) {
        if (endOfDayMillis(cal, lesson.timeEnd) > createdAt) return dayIsoOf(cal)  // :116
    }
}
return null
```

**Цепочка вызовов (полная):**

1. `TasksScreen.kt:1086-1108` — сохранение: `deadlineDate = task?.deadlineDate ?: ""` → новое задание всегда с пустым дедлайном.
2. `TaskRepository.addTask/getPendingTasksForGroup` → `TaskDao.getPendingTasksForGroup` (`TaskDao.kt:25-26`, `isCompleted = 0`).
3. `AppViewModel.kt:172-180` — `pendingTasks` (scope: текущая группа).
4. `MainScreen.kt:338-341` → `pendingTasksFromVm`.
5. `ScheduleScreen.kt:310-333` — `remember(lessons, pendingTasks, activeDayOfWeek, selectedDateString, nowMinutes)` → `HomeworkMarkers.markerLessonTypes(...)`.
6. `HomeworkMarkers.kt:45-58` — цикл по урокам дня × заданиям; `:60` `result.getOrPut(lesson.lessonNumber)`.
7. `ScheduleScreen.kt:1029-1030`, `:1094-1095`, `:1151-1157` — отрисовка `HomeworkBadge`.

**Да, это и есть баг.** Формально: предикат «бейдж виден» = `day == единственный_день`, тогда как требуется `startDay ≤ day ≤ deadline` (или `day ≥ startDay` при отсутствии дедлайна). Для предмета, встречающегося 2 раза в неделю, множество дней с бейджем имеет мощность 1 — ровно то, что описал заказчик: «на второй такой же урок уже не показывается».

Дополнительное следствие, которое заказчик не сформулировал, но оно тяжелее: `targetIso` вычисляется от **неизменного** `createdAt`, поэтому после того, как этот единственный день прошёл, **бейдж не появляется уже никогда** — хотя задание остаётся `isCompleted = 0` и висит в списке заданий. ДЗ «выпадает» из расписания навсегда на следующий день после первого показа.

### 2. Какая семантика ожидается заказчиком?

В репозитории **нет** ни одного документа, задающего «на каких уроках гореть бейджу». Проверено grep'ом по всем `*.md` в корне репо (`домашн|ДЗ|дедлайн|бейдж|homework|Homework|JJ1`) и в `DECISIONS.md`:

- `MASTER-PLAN.md:105-108` (N18) — только **вид** бейджа: кликабельность, выразительность, мультицвет по типам. Про «на каких уроках» — ничего.
- `MASTER-PLAN.md:474` (W24) — только вёрстка: «бейдж выталкивает предмет».
- `MASTER-PLAN.md:583` (V16) — только форма: «бейдж типа = текстовый чип в правом верхнем углу».
- `MASTER-PLAN.md:191-200` (ФАЗА 3) — редактирование задания и напоминалки; текстом: «Форма задания (категория/предмет/что сделать/**срок**) заказчика в целом устраивает — не ломать» и «кнопка рядом со **Сроком сдачи**». То есть **срок/дедлайн — заявленная часть формы**, которой в UI нет.
- `MASTER-PLAN.md:974-986` (JJ1) — только про расхождение написаний предметов.
- `DECISIONS.md` — про задания ничего содержательного (только «напоминания — пусть сами смотрят»).

**Вывод:** семантика «одно вхождение» — не требование, а побочный продукт ИИ-реализации; документированного контракта нет. Опора для корректной семантики — дословная жалоба заказчика («на второй такой же урок уже не показывается» ≠ ожидаемое) плюс требование «срок сдачи» в форме. Ожидаемое поведение сформулировано ниже в разделе **«Спецификация корректного поведения ДЗ»**: бейдж на **всех** уроках предмета в окне `[первый урок после создания … дедлайн]`, при отсутствии дедлайна — до отметки «выполнено».

### 3. Почему «на второй такой же урок уже не показывается» без дедлайна и как чинить?

Потому что отсутствие дедлайна — это **не** «нет ограничения», а принудительный переход в ветку `resolveNextOccurrenceIso`, которая по построению возвращает первую подходящую дату и обрывает поиск (`return` внутри цикла, `:116`). Второй день недели просто никогда не проверяется на совпадение: сравнение идёт на равенство с одним `dayIso` (`:57`).

**Как чинить (рекомендация):** ни набор дат, ни явная привязка к уроку — а **вычисляемый предикат активности**:

```kotlin
fun isHomeworkActiveOn(
    task: StudentTaskEntity,
    dayIso: String,                    // день отрисовки
    lesson: LessonEntity,              // конкретный урок (subjectKey уже проверен)
    nowMillis: Long,
): Boolean
```

- `task.isCompleted` → `false` (выполнено — не горит);
- `startIso = firstLessonDayOnOrAfter(task.createdAt, subjectKey, weeklyLessonsByDow)`; `dayIso < startIso` → `false`;
- `task.deadlineDate` задан → `dayIso <= deadlineIso` (сравнение по epoch, не по строке);
- дедлайн не задан → окно открыто до `isCompleted`.

Почему **не** «набор дат»: набор пришлось бы пересчитывать при каждом пересинке расписания — а `replaceSyncedLessons` (`ScheduleRepository.kt:668-679`) делает `replaceForDate` (delete+insert по дате), т.е. состав уроков меняется; кэшированный набор дат мгновенно устареет.

Почему **не** «явная привязка к уроку/дате в задании» (`lessonId`): идентификаторы уроков нестабильны (`replaceForDate` их пересоздаёт), а `pruneOldLessons` (`:658-664`) удаляет уроки по датам — задание останется с висящей ссылкой. Хранить *дату* урока можно, но это ручной выбор, который ломает главный сценарий («создал ДЗ — бейдж сам появился на уроке»). Привязка нужна только для опциональной фичи «на какой урок задано» (см. спецификацию, п. 8) — как отдельная nullable-колонка, не как основа матчинга.

### 4. Гейты `subjectsMatch`: ложные срабатывания и промахи

Порог 0.8 Левенштейна сам по себе терпим; **проблема в contains-эвристике** (`HomeworkMarkers.kt:82-87`), которая при длине обеих сторон ≥6 символов считает совпадением вхождение подстроки в канонические имена:

```kotlin
normLesson.length >= 6 && normTask.length >= 6 &&
    (normLesson.contains(normTask, ignoreCase = true) ||
        normTask.contains(normLesson, ignoreCase = true))
```

Поскольку обе стороны уже канонизированы в официальные имена, **любой предмет, чьё имя является префиксом/подстрокой другого официального предмета, склеивается с ним**. Конкретные пары (обе стороны — реальные записи `MpkCurriculum.ALL_SUBJECTS`):

| Пара | Где в курикулуме | Что происходит |
|---|---|---|
| «Математика» ↔ «Математика в профессиональной деятельности» | `MpkCurriculum.kt:19` и `:20`, `:431`, `:698` | contains → **match**, бейджи протекают на чужой предмет |
| «Физика» ↔ «Физика твёрдого тела» | `:22` и `:437` (4 курс, спец. «О») | contains → **match** |
| «Делопроизводство» ↔ «Кадровое делопроизводство» | `:84` и `:106` (спец. «Д») | contains → **match** |
| «Электротехника» (сырое имя из расписания, не канонизируется) ↔ «Электротехника с основами электроники» | `:780` | contains → **match** |

Ложные **промахи** (хуже для заказчика, потому что «домашки не видно»):

| Пара | Причина |
|---|---|
| «Физкультура» ↔ «Физическая культура и здоровье» | UI графика показывает короткое имя «Физкультура» (`SubjectFormatter.kt:253`, `PREDEFINED_SHORT_NAMES`), пикер заданий — официальное. `normalize("Физкультура")` не находит канон (score 0.17 < 0.6) → остаётся «Физкультура»; `levenshteinSimilarity("физическая культура и здоровье","физкультура") ≈ 0.44 < 0.8` → **нет бейджа** |
| «Ин. яз. (проф)» ↔ «Иностранный язык (профессиональная лексика)» | та же механика (короткое имя из `PREDEFINED_SHORT_NAMES:260`) |
| «Хиимя» ↔ «Химия», «Физикка» ↔ «Физика» | опечатка в предмете короче 6 символов: и contains-, и Левенштейн-ветки закрыты гейтом `length >= 6` (`:84-91`) → фаззи для коротких имён **выключен полностью** |
| «ТОЭ» с опечаткой («ТЭО») | 3 символа → ни одна эвристика не работает |

Проверено и **корректно не матчится** (не баг): «Информатика» ↔ «Информационные технологии» (contains нет, similarity ≈ 0.42), «Электротехника» ↔ «Электроника», «Основы права» ↔ «Основы менеджмента». Это зафиксировано тестами `Jj1SubjectsMatchTrapTest.kt:46-51`.

Отдельно: `SubjectFormatter` содержит **две визуально почти одинаковые аббревиатуры с разными целями** — `"Делопроизвод" → "Документоведение"` (`:40`) и `"Делопро" → "Делопроизводство"` (`:123`). Это не доказанный баг (возможно, так размечено на сайте колледжа), но обязано быть зафиксировано тестом-ловушкой, иначе любая правка карты аббревиатур молча перекинет предмет.

Про «Моя специальность» и «КУРЧ» из брифа:
- «Моя специальность» — это **заголовок экрана** (`CollegeScreen.kt:308`, `:525`), а не предмет расписания; ложных срабатываний не даёт (в `ALL_SUBJECTS` отсутствует, `normalize` вернёт как есть → self-match по `equals`).
- «КУРЧ» → канон «Кураторский час» (`SubjectFormatter.kt:177-178`), но «Кураторский час» **отсутствует** в `MpkCurriculum`, поэтому выбрать его в пикере задания нельзя — только вручную ввести «КУРЧ». Ложных срабатываний нет, но и ДЗ по кураторскому часу корректно не заведёшь.

### 5. `lessonPassed` / `day.isPast`: исчезает ли бейдж после пары?

Да, и это отдельный дефект, усиливающий P0.

`ScheduleScreen.kt:317-323` считает контекст дня:

```kotlin
val isToday = dayIsoOf(realNow) == dayIso
val isPast  = dayIsoOf((realNow.clone() as Calendar).apply { add(DAY_OF_YEAR, -1) }) > dayIso
```

- `isPast` — **строковое** сравнение ISO (`yyyy-MM-dd`), поэтому лексикографически корректно только для ISO. Семантика же неверна: `isPast == true` лишь когда `dayIso < вчера`. Следствия:
  - **сегодня** → `isPast = false` (ок);
  - **вчера** → `isPast = false` → бейджи на вчерашних (давно прошедших) уроках **показываются**;
  - **позавчера и раньше** → `isPast = true` → `markerLessonTypes` возвращает `emptyMap()` (`HomeworkMarkers.kt:42`).
- `lessonPassed` (`HomeworkMarkers.kt:122-135`) действует **только** при `isToday` и гасит бейдж, как только `endMinutes <= nowMinutes`, т.е. **сразу после окончания пары**:

```kotlin
if (!day.isToday) return false          // :127
val endMinutes = parseMinutes(lesson.timeEnd) ?: return false   // :133 fail-open
return endMinutes <= nowMinutes         // :134
```

  Во время пары бейдж виден (правильно), после звонка — исчезает. `rememberNowMinutes()` (`ui/util/TodayProvider.kt:44-56`) тикает раз в минуту и стоит в ключах `remember` (`ScheduleScreen.kt:312`), поэтому бейдж пропадает «сам», без действий пользователя.

**Итог по вопросу:** компонент ведёт себя несогласованно — вчерашние прошедшие уроки бейдж показывают, а сегодняшние прошедшие нет. Для студента это выглядит ровно как жалоба заказчика: «открыл расписание после пар — домашки нет». ДЗ, которое он ещё не сделал, исчезает из расписания в момент, когда оно нужнее всего.

### 6. JJ1 («предметы в Расписании и в Заданиях РАЗЛИЧАЮТСЯ») — устранён?

**Симптом — да, корневая причина — нет.**

Устранено: канонизация через `SubjectFormatter.normalize` (карта `MPK_SCHEDULE_ABBREVIATIONS` на 236 записей + `MpkCurriculum.ALL_SUBJECTS` + фаззи-фолбэк при score ≥ 0.60), кейсы «СистТехнОргСер»/«СисиТехОрг»/«БухУчёт» закрыты и закреплены (`Jj1SubjectsMatchTrapTest.kt:12-43`, `SubjectFormatterCollisionTest.kt`, `HomeworkSubjectsMatchTest.kt:37-44`). В CHANGELOG 2.2 это записано как исправление.

Не устранено (архитектурно):
1. **Канонизация живёт только на чтении.** В БД `StudentTaskEntity.subjectName` хранится «как выбрано/как набрано» (`StudentTaskEntity.kt:15`), канон вычисляется каждый раз через lazy `officialSubjectName` (`LessonEntity.kt:46-48`) и повторный `normalize` внутри `subjectsMatch`. Любая правка карты аббревиатур меняет трактовку **уже сохранённых** заданий и бэкапов — обратной совместимости нет.
2. **Нет канонического ключа предмета** (id/enum). Сопоставление — сравнение строк с эвристиками, поэтому каждая новая эвристика (например contains) рождает новый класс ошибок — см. находку P1-5.
3. **Двойная нормализация в `subjectsMatch`** (`:72-73`, `:80-81`): урок уже канонизирован (`officialSubjectName`), но нормализуется снова; задача нормализуется дважды в двух видах (`rawTask` без lowercase и без канона, `normTask` с каноном). Ветка `:93-97` (Левенштейн по `foldedRawLesson`/`rawTask`) в норме недостижима, т.к. `foldedRawLesson ≈ normLesson` — мёртвый код, маскирующий проблемы.
4. **Порог 0.60 в `normalize` может «уехать» в чужой предмет** (`SubjectFormatter.kt:565-578`): при неудачной канонизации возвращается ближайший официальный предмет, а не исходная строка, — и дальше `equals` считает это совпадением.

## Находки

### [P0] Бейдж ДЗ привязан к одному календарному дню
- **Где:** `app/src/main/java/com/politex/util/HomeworkMarkers.kt:56-57`, `:101-120`; потребитель `app/src/main/java/com/politex/ui/screens/ScheduleScreen.kt:310-333`
- **Симптом/влияние:** ДЗ показывается только на одном уроке предмета (первое вхождение после создания). Второй и последующие уроки того же предмета (другой день недели / другая пара) — без бейджа. После того как этот день прошёл, бейдж не появляется уже никогда, хотя задание остаётся невыполненным. Это дословно жалоба заказчика.
- **Root cause:** `resolveNextOccurrenceIso` возвращает `String?` — **единственный** iso-день (выход по `return` из цикла на первом подходящем уроке, `:116`), а `markerLessonTypes` проверяет равенство дня: `targetIso != null && sameIsoDay(targetIso, day.dayIso)` (`:57`). Предикат «видимости» по построению имеет мощность 1 на предмет. `task.createdAt` неизменен → окно не расширяется со временем.

## Спецификация корректного поведения ДЗ

Документированного контракта в репозитории нет (см. ответ на вопрос 2), поэтому фиксирую предлагаемую семантику — она выводится из жалобы заказчика и из требования «срок сдачи» в форме задания.

### Термины
- **Предмет (subjectKey)** — канонический идентификатор предмета (официальное имя из `MpkCurriculum.ALL_SUBJECTS` + `specialtyCode`/`course`). Сопоставление «Расписание ↔ Задания» — **только** по нему (плюс явный список алиасов/опечаток).
- **Окно активности ДЗ** — множество календарных дней, в которые бейдж должен гореть на уроках этого предмета.
- **Вхождение** — конкретная пара в конкретный день недели (Пн пара 2, Ср пара 3 — два разных вхождения одного предмета).

### Правила

1. **Бейдж горит на ВСЕХ уроках предмета внутри окна активности** — на каждом вхождении, на каждой паре, в каждом дне недели. Именно это нарушено сейчас (P0-1).
2. **Начало окна.** Первый урок этого предмета, время окончания которого позже `createdAt` (если урок сегодня ещё не закончился — окно открыто с сегодня; иначе — со следующего вхождения). Это ровно текущая логика `resolveNextOccurrenceIso`, но как *нижняя граница*, а не как единственный день.
3. **Конец окна.**
   - `deadlineDate` задан → окно закрывается **включительно** днём дедлайна (`dayIso <= deadlineIso`). Если уроков предмета в этот день нет — окно всё равно включает все уроки до него.
   - `deadlineDate` не задан → окно **открыто бессрочно** до отметки «выполнено» или удаления задания.
4. **Выполненное задание не горит нигде** (`isCompleted = true` → бейджа нет, независимо от окна и дедлайна). Удалённое — тем более.
5. **Просроченное невыполненное ДЗ не скрывается.** Дедлайн в прошлом, `isCompleted = false` → бейдж продолжает гореть (по желанию — другим цветом / с пометкой «просрочено»). Молчаливое исчезновение недопустимо: это потеря задания.
6. **Внутри дня бейдж не зависит от хода времени.** Он не гаснет по звонку и не появляется только в узком окне (см. P1-4). Расписание — статичная карточка дня; «прошло/не прошло» — отдельное визуальное состояние, не удаление бейджа.
7. **Прошедшие дни (архив).** Для дат **раньше сегодняшней** бейдж не рисуется (или рисуется приглушённым — решение за заказчиком, по умолчанию не рисуется). Определяется календарно (`dayIso < todayIso` по epoch), а не строковым сравнением с «вчера».
8. **«Следующий урок»** (для навигации/подсказок) — первое вхождение предмета с `timeEnd > now`. Используется для тапа по бейджу и будущих напоминаний; на отрисовку бейджа не влияет.
9. **Несколько заданий одного предмета** → несколько бейджей (по типу), дедуп по типу в рамках пары (уже есть `distinct()`, `HomeworkMarkers.kt:64`). N18(в) сохранён.
10. **Ключ отрисовки — слот урока**, а не номер пары (P2-9): бейдж принадлежит конкретному уроку слота, не «всем парам №2».
11. **Опционально (новая фича, отдельной задачей).** Явная привязка «на какой урок задано»: nullable-колонка `pinnedLessonDateIso` (дата, не `lessonId` — id нестабильны из-за `replaceForDate`). Если задана — бейдж горит только на этом дне (явное перекрытие общего окна). По умолчанию не задана, сценарий заказчика не требует ручных действий.
12. **Даты.** Единый кодек: в UI и в БД — `дд.ММ.гггг` **или** ISO, но строго одним способом и с чтением обоих форматов; сравнение — только через epoch/`Calendar`. ISO-строки не сравнивать лексикографически вне ISO-домена.

### Граничные случаи (обязательные к покрытию тестами)
- Задание создано после последнего урока предмета сегодня → бейдж со следующего вхождения.
- Задание создано в 23:50 → не должно «прилипать» к сегодняшнему уроку.
- Предмет не встречается в расписании вовсе → бейдж нигде (не ошибка), но в списке заданий — пометка «предмета нет в расписании».
- Расписание не загружено (`allGroupLessons == null` / пусто) → бейджей нет (текущее поведение корректно, но должно быть покрыто тестом).
- Пересинк расписания (`replaceSyncedLessons`) не меняет окно активности (вычисляется на лету).
- Группа сменилась → задания другой группы не протекают (сейчас `pendingTasks` скоупится по группе: `AppViewModel.kt:172-180`, `TaskDao.kt:25-26` — корректно).
- Задание с предметом из другой специальности (кастомный ввод) → не матчится с чужими предметами той же группы.

## Приложение: точная трассировка бага заказчика

Сценарий: группа 41О, предмет «Математика» стоит в Пн (пара 2) и Ср (пара 3). Сегодня Пн 2026-11-02, 10:00. Студент создаёт ДЗ по математике **без срока** (срок задать негде — P0-2).

1. `TasksScreen.kt:1086` → `dueIso = ""`; `:1097` → `deadlineDate = ""`; `:1098` → `createdAt = 1762...` (Пн 10:00).
2. `TaskDao.getPendingTasksForGroup("41О")` возвращает задание (`isCompleted = 0`).
3. `ScheduleScreen.kt:310-333`: `homeworkByLesson = markerLessonTypes(dayLessons = <Пн>, day = DayContext("2026-11-02", isToday = true, isPast = false), ..., pendingTasks = [task])`.
4. `HomeworkMarkers.kt:42` — `isPast = false`, продолжаем.
5. `:46` — урок Пн пара 2 (`timeEnd = 11:30`) → `lessonPassed` = false (11:30 > 10:00) → не пропускаем.
6. `:51` `subjectsMatch("Математика","Математика")` = true.
7. `:53` дедлайн пуст → идём в ветку `else`.
8. `:56` `resolveNextOccurrenceIso(createdAt = Пн 10:00, "Математика", weeklyLessonsByDow)`:
   - `offset = 0` → `dow = 1` (Пн) → уроки Пн, фильтр по предмету → пара 2;
   - `:115` `endOfDayMillis(Пн, "11:30") = Пн 11:30 > Пн 10:00` → `return "2026-11-02"`.
9. `:57` `sameIsoDay("2026-11-02", "2026-11-02")` = true → бейдж на Пн, пара 2. ✅
10. Студент открывает Ср (2026-11-04): `day.dayIso = "2026-11-04"`, `sameIsoDay("2026-11-02", "2026-11-04")` = **false** → бейджа нет. ❌ — ровно «на второй такой же урок уже не показывается».
11. Через неделю (Пн 2026-11-09): `targetIso` по-прежнему `"2026-11-02"` (он вычисляется от неизменного `createdAt`) → бейджа нет ни в один день, **никогда**. Задание при этом висит в «Уроках» как невыполненное.
12. Если тот же студент откроет расписание в Пн 2026-11-02 в 12:00 (после пары), бейджа тоже не будет: `lessonPassed` (`:134`) скроет урок. Два независимых механизма дают один и тот же симптом.

**Минимальное изменение, закрывающее шаг 10 и 11:** заменить сравнение `sameIsoDay(targetIso, day.dayIso)` на проверку интервала `dayIso in startIso..(deadlineIso ?: ∞)` с учётом `isCompleted` (шаг 1 плана).

# 06 — АДВОКАТ ДЬЯВОЛА: атака на идею отдельного приложения для преподавателей

> Роль: скептик. Задача — не утопить проект, а оставить только то, что выдержит удар.
> Фаза 1 (изоляция): чужих бумаг не видел, бью по очевидным кандидатам.
> Каждый тезис: **Аргумент → Steelman → Вердикт**. Вероятности — экспертные оценки, [ASSUMPTION] где гадаю.

---

## 1. Топ-10 причин провала

### 1.1. Рынок из 100 человек, установят 10, будут пользоваться 3
**Вероятность: 85%. Последствия: проект-зомби — формально живой, фактически мёртвый.**
**Аргумент:** Аудитория — ~100 преподавателей 45–60 лет, технически скептичных. Ученическое приложение уже прошло этот путь с аудиторией в сотни раз больше (студенты). Реалистичная воронка: узнают 50 → установят APK вне Play Market 10–15 → останутся через месяц 3–5. Любая фича, оценённая «на глаз» для 3 пользователей, — оверинжиниринг.
**Steelman:** Даже 3 активных преподавателя — это 3 человека, которые влияют на сотни студентов; через них можно продвигать и ученическое приложение. Качество аудитории важнее количества.
**Вердикт: ПРИНЯТО ЧАСТИЧНО.** Продвижение через преподавателей реально, но для этого не нужно отдельное приложение — хватит режима в существующем (см. §5). Отдельный билд ради 3 человек не окупается.

### 1.2. Киллер-фича УЖЕ есть в ученическом приложении
**Вероятность: 90%. Последствия: отсутствие причины для установки.**
**Аргумент:** Ученическое приложение v2.5 уже показывает расписание любого преподавателя (сегодня/завтра/календарь, офлайн-кэш). Преподаватель может открыть его и посмотреть своё расписание. Вопрос «зачем ставить второе приложение, которое делает то же самое?» не имеет ответа без уникальной фичи — а все кандидаты на уникальность (§2) бьются.
**Steelman:** Ученическое приложение «про студентов»: преподавателю 55 лет некомфортно в интерфейсе, рассчитанном на подростков; своё расписание надо искать через поиск по ФИО. Отдельное приложение = «моё расписание сразу на главном экране».
**Вердикт: STEELMAN СИЛЬНЕЕ, ЧЕМ ОЖИДАЛОСЬ** — но решается одним экраном «Мой преподаватель» в существующем приложении (ярлык на конкретного человека), а не форком. Дифференциация через UI-режим, не через новый продукт.

### 1.3. Данные с сайта нерегулярные — «приложение врёт» = репутационный удар
**Вероятность: 70%. Последствия: критические для доверия.**
**Аргумент:** Расписание парсится с .doc, который публикуют нерегулярно и с правками. В ученическом приложении stale-данные прощают: студент сверился с Viber — и ладно. У преподавателя цена ошибки выше: он может пропустить пару или прийти не в ту аудиторию. Первый же случай «приложение показало не то» — и по преподавательской разнесётся «эта штука врёт». Отмыться студенту-одиночке практически невозможно.
**Steelman:** Преподаватель знает своё расписание лучше любого приложения; он использует его как справочник по аудиториям/группам, а не как истину. Плюс видна дата парсинга — честный дисклеймер снимает претензии.
**Вердикт: ПРИНЯТО ЧАСТИЧНО.** Дисклеймер + дата данных обязательны. Но для аудитории, которая НЕ прощает ошибок (преподаватели), продукт на нерегулярном источнике — мина замедленного действия.

### 1.4. Замены не формализованы — единственная настоящая боль недоступна
**Вероятность: 80%. Последствия: приложение не решает главную задачу преподавателя.**
**Аргумент:** Замены сообщают в Viber-чатах. Машинного канала нет. Значит, приложение не может показать главное — «что изменилось сегодня». Всё остальное (базовое расписание) преподаватель и так знает наизусть. Продукт, который не знает замен, для преподавателя бесполезен по определению.
**Steelman:** Можно дать преподавателю кнопку «отметить замену у себя» — персональный слой поверх базового расписания, хранится локально.
**Вердикт: АРГУМЕНТ ВЫИГРЫВАЕТ.** Ручная отметка собственной замены = преподаватель вводит данные, которые уже знает, ради экрана, который ему это покажет завтра. Ценность ≈ 0. Без формального канала замен от учебной части (см. условие №2 в §6) отдельное приложение бессмысленно.

### 1.5. Двойная поддержка одним разработчиком
**Вероятность: 95% (это не риск, а факт). Последствия: деградация ОБЕИХ приложений.**
**Аргумент:** Баг-фиксы ×2, релизы ×2, тесты ×2, парсинг ×2 (§3 подробнее). Разработчик один, заказчик — студент с учёбой. Каждый час на второе приложение — час, украденный у первого, у которого аудитория на порядки больше.
**Steelman:** Если кодовая база общая (модуль, а не форк), инкрементальная стоимость второго билда мала — 90% кода переиспользуется.
**Вердикт: ПРИНЯТО ПРИ УСЛОВИИ.** Общий модуль расписания/парсинга — жёсткое требование. Форк кодовой базы = автоматический отказ от идеи. [ASSUMPTION: сейчас это будет форк или copy-paste — типичный путь таких проектов.]

### 1.6. Аудитория 45–60 лет и установка вне Play Market
**Вероятность: 75%. Последствия: воронка установки схлопывается.**
**Аргумент:** [ASSUMPTION: распространение через APK/GitHub, как у ученического приложения.] Для студента «поставить APK» — рутина. Для преподавателя 55 лет — страшное действие: «а вдруг вирус», «а почему не из магазина», «у меня Xiaomi, он ругается». Google Play для студенческого проекта закрыт по стоимости/верификации [ASSUMPTION]. Половина потенциальных пользователей отвалится на шаге установки.
**Steelman:** Установку можно провести очно: студент-разработчик подходит и ставит сам за 2 минуты; преподаватели лояльны к «нашему, политеховскому».
**Вердикт: ПРИНЯТО ЧАСТИЧНО.** Очная установка работает, но превращает разработчика в службу поддержки «на ногах» — каждый сбой = «найди меня в коридоре и почини». Масштабируется плохо. PWA-версия (§5) снимает проблему целиком.

### 1.7. Администрация может воспринять как самодеятельность
**Вероятность: 50%. Последствия: запрет/конфликт вместо поддержки.**
**Аргумент:** Приложение ДЛЯ ПРЕПОДАВАТЕЛЕЙ от студента, без санкции администрации, с ФИО/телефонами/фото сотрудников внутри — может быть воспринято как «студент учит преподавателей работать» и как теневая обработка персональных данных сотрудников. Замдиректора по УР одним словом закрывает проект. Преподаватели, получившие установку «не пользоваться», подчинятся.
**Steelman:** Ученическое приложение уже живёт 15+ версий и содержит те же данные — прецедент есть, администрация как минимум в курсе. Расширение на преподавателей — естественный следующий шаг, который можно подать как подарок колледжу.
**Вердикт: STEELMAN СИЛЕН**, но письменное добро администрации всё равно обязательно (§6, условие №1) — устно проект живёт до первой жалобы.

### 1.8. Персональные данные: телефоны, email, фото преподавателей
**Вероятность: 40% (что возникнет вопрос), последствия: серьёзные (см. §4).**
**Аргумент:** teachers.csv содержит ФИО, должность, кабинет, телефон, email и ссылку на фото. Преподавательское приложение может распространиться за пределы колледжа (скинули в общий учительский чат, на форум) — и база из 100 сотрудников с контактами утекает в публичное поле. Закон РБ «О защите персональных данных» (№ 99-З) формально требует цели и согласия.
**Steelman:** Данные опубликованы самим колледжем на официальном сайте; приложение — лишь удобный канал к уже публичным данным. Ученическое приложение делает то же самое без последствий.
**Вердикт: АРГУМЕНТ СИЛЬНЕЕ.** «Колледж опубликовал» ≠ «студент может перерабатывать и распространять в своём продукте». Минимум: убрать фото и личные мобильные из преподавательского билда, оставить сайт как первоисточник, добавить механизм удаления по запросу (§4).

### 1.9. Расхождение парсинга между двумя приложениями
**Вероятность: 60%. Последствия: катастрофа доверия.**
**Аргумент:** Два приложения, два парсера (или два форка одного парсера), один .doc на сайте. Рано или поздно ученическое показывает одно расписание, преподавательское — другое (разные версии кэша, разный момент парсинга, разъехавшийся код). Преподаватель сравнивает со студенческим — расхождение. Объяснить это аудитории из §1.6 невозможно.
**Steelman:** Один общий модуль парсинга + один релизный цикл = расхождения исключены конструктивно.
**Verdict: ПРИНЯТО ПРИ ТОМ ЖЕ УСЛОВИИ** — общий модуль или ничего. Но даже общий модуль не спасает от разных моментов обновления кэша на устройствах; нужен visible timestamp данных в обоих приложениях.

### 1.10. Bus factor: студент выпустится — приложение-сирота
**Вероятность: 60% в горизонте 2–3 лет. Последствия: хуже, чем если бы приложения не было.**
**Аргумент:** [ASSUMPTION: разработчик — студент этого же колледжа.] Через 1–2 года он выпускается. Ученическое приложение переживёт: аудитория студентов обновляется и давит на поддержку. Преподавательское — умрёт тихо: 3 пользователя 55+ не найдут нового разработчика, а сломанный сайт/формат .doc окончательно добьёт парсинг. Для преподавателей «приложение, которое бросили» = подтверждение их скепсиса на годы вперёд, с репутационным шлейфом и для ученического.
**Steelman:** 15+ версий за время учёбы — темп такой, что проект явно переживёт выпуск; можно передать код следующему поколению кружка/наследнику.
**Verdict: ПРИНЯТО ЧАСТИЧНО.** Передача наследнику реалистична для одного приложения; убедить наследника тянуть два — нет.

**Итог §1:** минимум 4 причины из 10 (1.2, 1.4, 1.5, 1.9) упираются в один корень: **у отдельного приложения нет уникальной ценности, а стоимость его содержания реальна.**

## 2. Атака на ожидаемые киллер-фичи

### 2.1. Нагрузка-статистика (сколько пар в неделю/месяц, по группам)
**Не нужно, потому что:** преподаватель знает свою нагрузку — она определена учебной частью официально и меняется раз в семестр. Цифра «22 пары в неделю» не управляет никаким его решением. Это фича-витрина: красиво на демо, мертва через неделю.
**Сломается, потому что:** считается из того же нерегулярного .doc. Пока сайт не обновил расписание — статистика неверна. Если нагрузка расходится с официальным документом учебной части (а разойдётся: правки, замены, деление групп) — «приложение врёт» (§1.3), теперь ещё и в цифрах, которые преподаватель может предъявить.
**Steelman:** Нагрузка полезна для переговоров о ставке/доплатах и для зав. отделением, а не для рядового преподавателя; историческая статистика за семестр («сколько пар я реально отработал») недостижима другими средствами.
**Вердикт: НЕ В MVP.** Если делать — только как производный экран из уже спарсенных данных, с дисклеймером «справочно, первоисточник — учебная часть». Ценность близка к нулю, риск расхождения — реален.

### 2.2. Журнал (отметки посещаемости/оценки)
**Не нужно, потому что:** в РБ существует официальный электронный журнал, куда преподаватели обязаны вносить оценки [ASSUMPTION: в колледже используется официальная система электронных журналов]. Второй журнал = двойной ввод. Ни один преподаватель не будет вводить оценки дважды — ни за что. Локальный журнал без сервера = данные живут на одном телефоне, теряются при замене устройства, юридической силы не имеют.
**Сломается, потому что:** посещаемость — чувствительные данные о несовершеннолетних студентах. Хранение ФИО студентов + оценок в приложении студента-разработчика без согласия, без шифрования, без учёта — это инцидент, ожидающий первого потерянного телефона.
**Steelman:** Личный черновик-блокнот («мои заметки по группам») полезен и никому не мешает, если хранится локально и не содержит чужих ПД в структурированном виде.
**Вердикт: КАТЕГОРИЧЕСКИ НЕ В v1** (это красная линия §7). Максимум когда-нибудь — свободные личные заметки без привязки к студентам.

### 2.3. Отметки замен (преподаватель сам отмечает замену)
**Не нужно, потому что:** преподаватель узнаёт о замене из Viber/по телефону от учебной части — ДО того, как откроет приложение. Отметить замену в приложении = продублировать факт, который он уже знает, ради того, чтобы приложение показало ему то, что он ввёл минуту назад. Ценность обратной записи нулевая.
**Сломается, потому что:** локальная отметка не синхронизируется ни с кем; на следующем семестре/после переустановки — потеряна; расхождение с ученическим приложением (§1.9) усугубляется: у преподавателя «замена», у студентов «пара по расписанию».
**Steelman:** Если отметка замены ОДНИМ ТАПОМ уезжает в ученическое приложение (студенты видят «пары не будет») — вот тогда это киллер-фича: преподаватель становится источником правды.
**Verdict: STEELMAN ЕДИНСТВЕННАЯ РЕАЛЬНАЯ КИЛЛЕР-ФИЧА** — но она требует сервера/канала доставки = красная линия MVP (§7) + согласие учебной части на то, что студенческое приложение — официальный канал замен. Без этого — не делать. Зафиксировать как кандидат v2+ при выполнении условий §6.

### 2.4. Материалы к урокам (файлы, планы, презентации)
**Не нужно, потому что:** материалы живут там, где их готовят — на рабочем ПК/флешке/в облаке. Телефон преподавателя 55 лет — последнее место, где он будет менеджить учебные файлы. Загрузка файла в приложение проще из проводника ПК, но приложение не десктопное — значит, фича мертва на входе.
**Сломается, потому что:** хранение файлов = сервер или потеря при переустановке; форматы (.doc, .ppt, .pdf) в мобильном WebView — вечная борьба; объем кэша на бюджетных Android [ASSUMPTION] съедается моментально.
**Steelman:** Ссылки (не файлы) на уже размещённые материалы (облако колледжа/репозиторий) дёшевы и полезны — «открыть материалы к паре» одним тапом из расписания.
**Вердикт: НЕ В MVP.** Ссылочный вариант возможен дёшево, но только если колледж уже где-то централизованно хранит материалы [ASSUMPTION: скорее всего нет — значит, и ссылаться не на что].

### 2.5. Уведомления до пары («через 20 минут пара, каб. 229»)
**Не нужно, потому что:** преподаватель с 10+ лет стажа знает своё расписание наизусть (сам его составлял по сути). Уведомление ценно только при ИЗМЕНЕНИИ — а изменений приложение не знает (§1.4). «Напоминать о неизменном» — самый быстрый путь к тому, чтобы уведомления выключили, а приложение удалили.
**Сломается, потому что:** локальные exact-алармы на Android 12+ убиваются battery-оптимизацией (особенно Xiaomi/Huawei — типичные телефоны этой аудитории [ASSUMPTION]); уведомление прозвонит не вовремя или не прозвонит вовсе — оба сценария хуже тишины. Уведомление по stale-кэшу = «приложение врёт» в самом агрессивном формате: само пришло и соврало.
**Steelman:** Уведомление в день, когда распарсенные данные ИЗМЕНИЛИСЬ («обновилось расписание на сайте — проверьте») — честно, дёшево и полезно.
**Вердикт: «ДО ПАРЫ» — НЕТ. «ДАННЫЕ ОБНОВИЛИСЬ» — да**, но это фича ученического приложения тоже, т.е. снова не дифференциатор.

**Итог §2:** из пяти киллер-фич четыре мертвы на входе, одна (2.3-steelman) требует инфраструктуры, которой нет и которая в MVP запрещена. **Уникальной ценности для отдельного приложения не осталось.**

## 3. Скрытые стоимости

| Статья | Одно приложение | Два приложения | Комментарий |
|---|---|---|---|
| Фикс бага парсинга | 1× | 2× (или 1× если общий модуль) | Баги парсинга .doc — самые частые [ASSUMPTION по истории проекта] |
| Релиз | 1× | 2×: сборка, подпись, тест на 2–3 устройствах, changelog, распространение APK | Релиз — не «нажать кнопку»: для APK-дистрибуции каждый выпуск = ручная логистика |
| Регрессионное тестирование | 1 матрица | 2 матрицы | Преподавательский билд должен теститься на устройствах 45–60-летней аудитории — бюджетные Android, старые версии ОС [ASSUMPTION] |
| Реакция на изменение сайта | 1 парсер чинить | 2 парсинг-пайплайна синхронизировать | Главный операционный риск: сайт поменял формат .doc в пятницу вечером — оба приложения врут до понедельника |
| Каждая новая фича | оценка ×1 | оценка ×1.3–1.6 даже при общем модуле [ASSUMPTION] | Два UI-контекста, два набора текстов/ассетов, два прогона приёмки |
| Поддержка пользователей | студенты (терпят) | + преподаватели (не терпят) | SLA «найти разработчика в коридоре» (§1.6) |

**Ключевой скрытый риск — расхождение (divergence):** даже при общем коде две точки релиза = два состояния данных у пользователей. Преподаватель и студент на одной паре видят разное расписание. Это не баг, это архитектурное свойство двух приложений, и лечится оно только общим модулем + общим релизным циклом + видимым timestamp данных.

**Steelman всего раздела:** если второе приложение — это буквально другой flavor того же Gradle-проекта (product flavor, общий модуль schedule-core, отдельный только UI-слой «Мои пары»), инкремент ≈ 10–20%, не 100%.
**Вердикт:** flavor вместо форка — единственная приемлемая форма «второго приложения». Любой copy-paste репозитория — запретить на уровне решения консилиума.

## 4. Юридическое/этическое (РБ)

**Факты:** teachers.csv в ассетах содержит ФИО, должность, кабинет, рабочий телефон, email и имя файла фото (фото тоже в ассетах [ASSUMPTION]).

1. **Правовой режим:** Закон РБ «О защите персональных данных» (07.05.2021 № 99-З). Обработка допустима, в частности, когда данные опубликованы самим субъектом/оператором публично — колледж публикует контакты сотрудников на официальном сайте намеренно (информирование обучающихся). **Но:** распространение данных студентом через СВОЁ приложение — отдельная обработка с отдельной целью. «Ученическое приложение» (цель: навигация студентов по колледжу) защищается логикой первоисточника слабее, чем «приложение для преподавателей», которое может разойтись куда угодно (§1.8).
2. **Фото** — самый тяжёлый элемент: биометрией в бытовом смысле не является, но узнаваемость личности даёт; риск претензии конкретного преподавателя («я не давал согласия на моё фото в студенческом приложении») максимален именно здесь. Дешёвая страховка: фото — только из официальной публикации на сайте, с атрибуцией источника и удалением по первому запросу.
3. **Личные vs рабочие контакты:** email вида `politech@minskedu.gov.by` и кабинетные телефоны — рабочие, риск низкий. Личные мобильные (формат 8-029-xxx при наличии [ASSUMPTION]) — риск высокий; в преподавательский билд не включать вообще.
4. **Этика бренда:** приложение с названием/атрибутикой колледжа от частного лица без соглашения — администрация может потребовать снять название (§1.7). Дисклеймер «неофициальное приложение, данные с официального сайта» обязателен.
5. **Механизм удаления:** любому преподавателю — возможность одним письмом удалить свои контакты/фото из приложения. Это и юридическая защита, и демонстрация добросовестности администрации.

**Steelman:** данные публичны, колледж сам их распространяет, ученическое приложение 15+ версий живёт без претензий — практика сложилась.
**Вердикт:** практика сложилась в серой зоне, которая терпит, пока продукт маленький и «свой». Отдельное преподавательское приложение расширяет поверхность распространения и повышает шанс, что вопрос зададут. Минимальный набор мер (рабочие контакты только, фото с сайта, дисклеймер, удаление по запросу, добро администрации) — дёшев; делать обязательно.

## 5. Минимальная жизнеспособная альтернатива (ЧТО СДЕЛАТЬ ВМЕСТО)

Ранжировано по стоимости снизу вверх:

### 5.1. «Мой преподаватель» — режим/экран в существующем приложении ⭐ РЕКОМЕНДАЦИЯ
Закладка «Моё расписание»: пользователь выбирает преподавателя один раз — его расписание становится главным экраном (сегодня/завтра/неделя), без поиска по ФИО каждый раз. Плюс ярлык на домашний экран Android (app shortcut) прямо на этого преподавателя.
- Стоимость: дни, не недели. Переиспользует 100% парсинга, кэша, UI.
- Снимает steelman из §1.2 («интерфейс про студентов») целиком.
- Ноль двойной поддержки, ноль рисков расхождения, ноль нового юридического периметра.

### 5.2. PWA-страница «Расписание преподавателя» (веб-версия)
Статическая страница/мини-сайт с теми же данными: открыл ссылку — увидел, «установить на главный экран» для желающих. Решает проблему установки APK для аудитории 45+ (§1.6) радикально: ссылку в Viber-чат преподавателей кинул — и всё, установок не надо.
- Стоимость: средняя (нужен генератор статики из тех же данных) [ASSUMPTION: данные уже есть в JSON после парсинга].
- Риск: «приложение врёт» остаётся (§1.3), аудитория шире = критика громче.

### 5.3. Отдельное приложение как Gradle flavor (если консилиум всё же решит «надо»)
Общий модуль schedule-core, отдельный только тонкий UI-слой. Единственная форма «отдельного приложения», которую я как скептик могу терпеть (§3).

### Когда альтернатива ЛУЧШЕ (честная оценка)
**5.1 лучше отдельного приложения ВСЕГДА, пока:** (а) нет формального канала замен от учебной части, (б) нет санкционированной фичи, требующей другого периметра данных (журнал, аккаунты), (в) кодовая база не отрефакторена в общий модуль. Все три условия сейчас ложны [ASSUMPTION]. **Отдельное приложение оправдано только как носитель фичи, которую НЕЛЬЗЯ положить в ученическое** — а все такие фичи-кандидаты либо мертвы (§2), либо красные линии (§7). Это замкнутый круг: чтобы оправдать отдельное приложение, нужна фича, требующая инфраструктуры, которая отдельному приложению запрещена.

## 6. Условия успеха: чек-лист «если да — делаем»

Отдельное приложение ОПРАВДАНО только если выполнены **ВСЕ пять**:

1. **☐ Письменное добро администрации** (директор или зам по УР): проект легитимен, снят риск §1.7, открыт путь к условию 2.
2. **☐ Формальный канал замен:** учебная часть согласна публиковать замены в машиночитаемом виде (хотя бы общая таблица/doc в фиксированном месте). Без этого приложение не знает главного (§1.4) и не отличается от ученического.
3. **☐ Спрос подтверждён, а не придуман:** ≥30 преподавателей (из ~100) лично сказали «поставлю и буду пользоваться» — опрос/интервью, не «мне кажется». Порог 30 взят с запасом ×3 к ожидаемым 10 установкам [ASSUMPTION].
4. **☐ Есть ≥1 фича, которую нельзя положить в ученическое приложение** и которая не является красной линией (§7). Кандидат один: отметка замены, уходящая студентам (§2.3) — и она сама требует условия 1+2.
5. **☐ Общий модуль с ученическим приложением** (Gradle flavor, schedule-core), а не форк: стоимость поддержки ×1.2, а не ×2 (§3).

**Правило:** 5/5 — делаем. 4/5 — делаем только если не выполнено №2 или №1 (тогда стоп, это фундамент). ≤3/5 — не делаем, делаем §5.1.
Сейчас по фактам подтверждено 0–1 из 5 [ASSUMPTION]. **Вердикт скептика: НЕ ДЕЛАТЬ отдельное приложение в этой итерации.**

## 7. Красные линии MVP — что КАТЕГОРИЧЕСКИ нельзя класть в v1

| Красная линия | Почему нельзя |
|---|---|
| **Аккаунты/регистрация/логин** | Solo-разработчик получает: хранение креденшелов, сброс паролей, поддержку «не могу войти», ответственность за утечку. Польза при 10 пользователях — нулевая. Любая идентификация = новый юридический периметр. |
| **Сервер/бэкенд** | Превращает бесплатный офлайн-продукт в инфраструктуру с uptime-обязательством, стоимостью хостинга, поверхностью атаки и дежурством «упало в 3 ночи». Всё текущее доверие построено на офлайн-кэше — не ломать архитектуру, которая работает. |
| **Журнал оценок/посещаемости студентов** | Данные о несовершеннолетних + дублирование официального журнала (§2.2) + нулевая юридическая сила + потеря данных на устройстве = скандал с учебной частью. Самая дорогая красная линия: одна потерянная БД = конец доверия администрации навсегда. |
| **Push-замены «от учебной части»** | Требует сервера (см. выше) И формальной интеграции, которой нет (§6, условие 2). Push с неверной заменой хуже тишины: он приходит сам и врёт активно (§2.5). Обещать то, что не можешь гарантировать, аудитории, которая не прощает, — репутационное самоубийство. |
| **Сбор любых данных от преподавателей (ввод форм, загрузка файлов)** | Каждый собранный байт = ответственность за его хранение/удаление по запросу (Закон № 99-З) + поддержка формата + миграции. Приложение v1 должно быть read-only витриной уже опубликованных данных — только так юридический риск минимален. |
| **Личные мобильные телефоны и фото сверх официально опубликованного** | §4. Расширение данных сверх первоисточника — единственное, за что могут предъявить реально, а не гипотетически. |

**Общий принцип красных линий:** v1 — **read-only, offline, без идентификации, без собранных данных**. Всё, что превращает читателя в писателя или витрину в систему учёта, — в v1 запрещено.

## Финальный вердикт скептика

**Идея отдельного приложения в текущих условиях НЕ проходит проверку.** Корневая проблема: все киллер-фичи либо уже есть в ученическом приложении (расписание преподавателя), либо мертвы на входе (статистика, журнал, напоминания), либо требуют инфраструктуры, запрещённой красными линиями MVP (отметки замен → сервер). Остаётся продукт-пустышка для 3 пользователей при двойной стоимости поддержки.

**Что делать вместо:** экран «Мой преподаватель» + app shortcut в существующем приложении (§5.1, дни работы, ноль новых рисков), опционально PWA-ссылка для тех, кто не ставит APK (§5.2). **Когда вернуться к идее:** когда выполнятся все 5 условий §6 — прежде всего письменное добро администрации и формальный канал замен. До тех пор отдельное приложение — это решение в поисках проблемы.

# Ревью: Преподаватели, учащиеся, контакты
_Дата: 2026-10-01. Область: teachers-contacts_

## Резюме и вердикт

Область рабочая, но главный баг заказчика подтверждён полностью и он **двухприродный: данные + код**.
В `teachers.csv` в колонках кабинета/телефона/e-mail **буквально лежит символ em-dash «—» (U+2014)** у 89 из 100 преподавателей. Парсер (`TeachersRepository`) читает его как есть, без нормализации, а UI (`CollegeScreen`) проверяет наличие контакта через `isNotBlank()` — «—» непустая строка, поэтому секция «КОНТАКТЫ» рисуется всегда и показывает «Кабинет: —», «Телефон: —», «E-mail: —».

Индексы колонок в парсере **корректные** (off-by-one нет) — гипотеза о смещении `getOrElse(4)/getOrElse(5)` опровергнута.

Побочно найден второй, более неприятный баг данных: **2 строки (48, 93) содержат 11 полей вместо 10** — из-за лишней пустой колонки у этих преподавателей «Педагогический стаж» показывает название ЦК, а «Квалификационная категория» — стаж.

Вердикт по области: **требует исправления перед релизом**. Фикс прочерков — дешёвый и точечный (одна функция нормализации в парсере). Фикс строк 48/93 — правка CSV.

## БАГ ПРОЧЕРКОВ — root cause (данные vs UI vs парсер)

### Вердикт: ДАННЫЕ + ПАРСЕР (нет нормализации) + UI (наивная проверка). Это НЕ placeholder самого UI.

Проверил предварительную гипотезу заказчика — она **верна**. «—» не подставляется интерфейсом; он физически лежит в CSV.

### Доказательство из teachers.csv

Файл: `app/src/main/assets/teachers.csv`, 100 строк, разделитель `;`, UTF-8 **без BOM** (первые байты `d0 a8` = «Ш», не `ef bb bf`).

Реальная раскладка колонок (0-based) по строке 1:
```
[0] Шатько Александр Викторович      -> name
[1] Директор ГУО "Минский ...        -> position
[2] Управление образовательным ...   -> subjects
[3] 229                              -> room      (index 3)
[4] 338-33-42                        -> phone     (index 4)
[5] politech@minskedu.gov.by         -> email     (index 5)
[6] 001_Shatko_...jpg                -> photo
[7] Администрация колледжа           -> department
[8] Свыше 15 лет                     -> experience
[9] Высшая                           -> category
```
Индексы парсера `room=getOrElse(3)`, `phone=getOrElse(4)`, `email=getOrElse(5)` — **совпадают с раскладкой, off-by-one отсутствует**.

Подсчёт «—» по колонкам (символ U+2014, байты `e2 80 94`):
```
col[3] room  : 89 из 100 строк = «—»
col[4] phone : 89 из 100 строк = «—»
col[5] email : 89 из 100 строк = «—»
```
Пример строки 13 (`awk -F';'`): room=`[—]`, phone=`[—]`, email=`[—]`.
Реальные контакты есть только у 11 преподавателей (администрация, строки 1-12 частично).

Вариант прочерка в данных **один** — em-dash «—» (U+2014). Обычного дефиса «-» или en-dash «–» как отдельного значения нет, но фикс обязан их покрывать на будущее.

### Цепочка проявления в коде

1. **Парсер, нет нормализации** — `TeachersRepository.kt:44-56`:
   ```kotlin
   val p = line.split(';')
   Teacher(
       room  = p.getOrElse(3) { "" },   // «—» проходит как есть
       phone = p.getOrElse(4) { "" },   // «—» проходит как есть
       email = p.getOrElse(5) { "" },   // «—» проходит как есть
       ...
   )
   ```
   Значение «—» сохраняется в модель `Teacher` дословно.

2. **UI, наивная проверка наличия** — `CollegeScreen.kt:1369`:
   ```kotlin
   val hasContacts = teacher.room.isNotBlank() || teacher.phone.isNotBlank() || teacher.email.isNotBlank()
   ```
   `"—".isNotBlank() == true` → секция «КОНТАКТЫ» показывается для всех 100 преподавателей.

3. **UI, отрисовка прочерков** — `CollegeScreen.kt:1381-1389`:
   ```kotlin
   if (teacher.room.isNotBlank())  InfoRow("Кабинет", teacher.room, onClick = { onOpenRoom(teacher.room) })
   if (teacher.phone.isNotBlank()) InfoRow("Телефон", teacher.phone)   // -> «Телефон: —»
   if (teacher.email.isNotBlank()) InfoRow("E-mail", teacher.email)    // -> «E-mail: —»
   ```

### Двухслойный фикс (lazy root-cause)

**Слой 1 — нормализация в парсере (корень, одна точка на все вызывающие).**
В `TeachersRepository.parseCsv` ввести нормализацию ячейки и прогнать через неё все поля. Критично: нормализовать **только ячейку, целиком состоящую из прочерка**, НЕ трогая дефисы внутри значения — иначе будут уничтожены реальные телефоны вида `338-33-42` и `260 85 32`.

```kotlin
// Все значения «нет данных» в teachers.csv кодируются прочерком. Важно: НЕ заменять
// дефис внутри значения (телефон «338-33-42»), а обнулять только ячейку-прочерк целиком.
private val BLANK_TOKENS = setOf("", "—", "–", "-", "−", "‒")   // U+2014 U+2013 U+002D U+2212 U+2012
private fun cell(p: List<String>, i: Int): String {
    val v = p.getOrElse(i) { "" }.trim()
    return if (v in BLANK_TOKENS) "" else v
}
```
Заменить `p.getOrElse(N){""}` на `cell(p, N)` для всех 10 полей. После этого `room`/`phone`/`email` у 89 преподавателей станут пустыми строками — и все 5 мест UI выше очистятся автоматически (список, карточка, гейт, навигация).

Проверить одним assert-тестом (минимальный чек):
```kotlin
// parseCsv на строке «A;B;C;—;—;—;p.jpg;D;E;F» даёт Teacher(room="", phone="", email="")
// а на «A;B;C;229;338-33-42;m@x.by;...» даёт room="229", phone="338-33-42" (дефис сохранён)
```

**Слой 2 — UI-гейт (оборона, уже почти готов).**
`hasContacts` на 1369 после слоя 1 заработает корректно сам (пустые строки → `isNotBlank()==false` → секция скрыта). Оставить как есть; он становится «бесплатной» защитой. Дополнительно ничем не менять — шильдик «КОНТАКТЫ» исчезнет у 89 преподавателей без правок разметки.

Итог: минимальный диф = ~6 строк в парсере, 0 строк в UI. Один корень закрывает все 5 проявлений.

## Прочие критичные баги

### TEA-02 — critical — строки 48 и 93 в teachers.csv имеют 11 полей: стаж и категория съезжают
**file:** `app/src/main/assets/teachers.csv:48,93`; парсер `TeachersRepository.kt:45-56`
**Root cause:** в двух строках после `room;phone;email` идёт **две** пустые колонки (`;;`) вместо одной под photo, поэтому все последующие поля сдвигаются на +1. Парсер позиционный (`getOrElse(7)=department`, `8=experience`, `9=category`) и не валидирует число полей.

Доказательство (строка 48, разбита по `;`):
```
1 Галимова Ирина Николаевна  2 Преподаватель  3 Специальные дисциплины
4 —  5 —  6 —  7 (пусто)  8 (пусто)  9 ЦК физической культуры и здоровья  10 2 года  11 без категории
```
В нормальной строке 10 полей; здесь 11 → лишняя пустая колонка 8. Что прочитает парсер:
- `photo = getOrElse(6)` = "" ✓ (случайно верно)
- `department = getOrElse(7)` = "" ✗ (должно быть «ЦК физической культуры и здоровья»)
- `experience = getOrElse(8)` = **"ЦК физической культуры и здоровья"** ✗ (должно быть «2 года»)
- `category = getOrElse(9)` = **"2 года"** ✗ (должно быть «без категории»)

**Проявление в UI:** `CollegeScreen.kt:1329-1330` покажет «Педагогический стаж: ЦК физической культуры и здоровья» и «Квалификационная категория: 2 года» — видимая порча данных у 2 преподавателей (Галимова, Бачило).
**Фикс:** убрать лишнюю пустую колонку в обеих строках CSV (`;;;;` → `;;;`), т.е. `...;—;—;—;;ЦК физической культуры и здоровья;2 года;без категории`. Опционально — защита в парсере: при `p.size != 10` логировать/пропускать, но источник — данные. Строка 93 (Бачило) идентична по структуре.

## Баги «через раз»

### TEA-03 — medium — мёртвая навигация: клик по «Кабинет: —» открывает карту с несуществующей комнатой
**file:** `CollegeScreen.kt:1381-1386` → `onOpenRoom(teacher.room)` → `215-219` (`mapRoom = room; navigateTo(MAP)`)
**Root cause:** строка кабинета кликабельна (`onClick != null`), а значение `room="—"` не пустое. Пользователь тапает «каб. —» и попадает на карту с комнатой «—», которой нет в `college_map.json` — пустой/сломанный экран карты.
**Проявление:** только у 89 преподавателей с прочерком; после фикса TEA-01 (room="") строка исчезнет и баг уйдёт сам. Отдельной правки не требует, но зафиксирован как самостоятельный симптом.

### TEA-04 — medium — список преподавателей показывает «каб. —»
**file:** `CollegeScreen.kt:1044-1045`
**Root cause:** тот же — `teacher.room.isNotBlank()` истинно для «—». В списке (не в карточке) под ФИО выводится «каб. —».
**Фикс:** покрывается нормализацией TEA-01 (room станет ""). Отдельно править не нужно.

### TEA-05 — medium — TeachersRepository парсит наивным split(';') без учёта кавычек; subjects с «;» развалят строку
**file:** `TeachersRepository.kt:44` (`line.split(';')`)
**Root cause:** в отличие от `StudentsRepository.splitRow` (корректный конечный автомат с учётом `"` и удвоенных кавычек, строки 104-128), парсер преподавателей режет строку тупо по `;`. Сейчас данные «чистые» (99 строк по 10 полей), поэтому не ломается, но это латентная мина:
- В `CollegeScreen.kt:1350` список дисциплин парсится как `teacher.subjects.split(';', ',')` — т.е. модель **ожидает** «;» внутри subjects. Но сама строка CSV уже разрезана по «;» → subjects никогда не может содержать «;» после парсинга. Противоречие: как только в CSV добавят преподавателя с «Математика; Физика» в колонке subjects, строка даст >10 полей и все колонки после subjects съедут (тот же класс бага, что TEA-02).
- Позиция 2 (`Директор ГУО "Минский политехнический колледж"`) содержит кавычки — сейчас они не экранированы и «;» внутри кавычек не обработается.
**Фикс:** переиспользовать `splitRow`-логику из `StudentsRepository` (вынести в общий util или скопировать конечный автомат) и/или заключать значения с «;» в кавычки в CSV. Минимально — задокументировать ограничение и не допускать «;» в subjects (тогда `split(';')` на 1350 — мёртвый код, оставить только `,`).

### TEA-06 — medium — surnameOf ломается на формате «И.И. Иванов» (инициалы впереди)
**file:** `TeacherInsights.kt:116-122`
**Root cause:** `surnameOf` берёт **первый** токен как фамилию: `raw.replace(digits,"").split(whitespace).firstOrNull()`. Для «И.И. Иванов» первый токен — «И.» → после trim → «и», а не «иванов». Значит `bySurname["и"]` не найдёт преподавателя, и `matchTeacher` вернёт null.
**Смягчение:** `teachers.csv` и (судя по тесту `TeacherInsightsTest.kt:93` — «Зыбин О.Л. /Купрейчик Н.А.») расписание используют формат «Фамилия И.О.», поэтому в текущих данных баг не проявляется. Но если во входящем расписании/документе встретится «И.И. Иванов», сопоставление молча отвалится (преподаватель не попадёт в «ВЕДЁТ У ВАШЕЙ ГРУППЫ»).
**Фикс:** определять фамилию как первый токен, начинающийся с буквы и длиной ≥ 3 (или первый токен без точки), а не просто первый. Покрыть тестом оба порядка.

### TEA-07 — medium (UX) — телефон и e-mail не кликабельны
**file:** `CollegeScreen.kt:1388-1389`
**Root cause:** `InfoRow("Телефон", teacher.phone)` и `InfoRow("E-mail", teacher.email)` вызываются **без** `onClick`, в отличие от кабинета. В проекте вообще нет `tel:`/`mailto:`/`ACTION_DIAL`/`ACTION_SEND`. Для раздела «Контакты» это UX-пробел: пользователь видит номер/почту, но не может тапнуть, чтобы позвонить или написать.
**Фикс (опционально, после TEA-01):** для непустых phone/email добавить `onClick` с `Intent(ACTION_DIAL, Uri.parse("tel:..."))` и `Intent(ACTION_SEND, ...mailto)`. Делать только для реальных значений (после нормализации), иначе «—» станет кликабельным мусором.

## Архитектура и ООП

- **Кэш `TeachersRepository`** (`:34-37`) — `@Volatile private var cached` в companion, процесс-глобальный, не инвалидируется. Для неизменяемого ассета это корректно и совпадает с паттерном `ScheduleScreen` (комментарий Б13). Гонка при первом параллельном вызове возможна (двойной парсинг), но безвредна — результат идемпотентен. **Не ломать.** (TEA-10, info)
- **`TeacherInsights`** — чистый класс без Android-зависимостей, логика сопоставления по фамилии+инициалам с защитой от тёзок: при >1 кандидате и отсутствии инициалов возвращает `null` (не угадывает) — хорошее решение. `matchTeacher` (`:76-107`) имеет разумный fallback по префиксу фамилии (≥5 символов).
- **Разделение flavors:** `StudentsRepository` и `StudentsScreens` лежат в `main` (компилируются в оба flavor), но экран достижим только через `isAdmin`-гейт (`CollegeScreen.kt:313,323`). Архитектурно приемлемо, dead code в standard — минорный размер, не баг.
- **`SubjectFormatter`** — три независимых словаря (`MPK_SCHEDULE_ABBREVIATIONS` abbr→full, `PREDEFINED_SHORT_NAMES` full→short, `PREDEFINED_ACRONYMS` full→acronym) + fuzzy-матчинг Левенштейна. Есть дубли ключей между картами («Основы права», «ТОЭ» и т.д.), что ожидаемо при разных направлениях маппинга. `getShortName`/`getAcronym` оба вызывают `normalize()` — при использовании всех трёх в одном экране `normalize` (с O(ALL_SUBJECTS) Левенштейном) прогоняется 3×. Перформанс приемлемый, но см. TEA-11 по корректности fuzzy-contains.

## Безопасность (students.csv, персональные данные)

- **students.csv (800 КБ, персональные данные) — только в `app/src/admin/assets/`.** В `main/assets/` его нет (проверено: там только `teachers_photos/`, `college_map.json`, `group_codes.csv`, `teachers.csv`). Стандартный flavor файл не получает. ✓
- **Crash у обычных пользователей исключён:** `StudentsRepository.loadStudents()` (`:33-40`) обёрнут в `try/catch(Exception)` → при отсутствии ассета в standard возвращает `emptyList()`, а не падает. Экран `StudentsDatabaseScreen` в standard просто показал бы пустой список, но он и так недоступен (гейт `isAdmin`). **Защита корректная — не ломать.** ✓ (TEA-12, positive)
- **ФИО учащихся в отчёт не копировались** (требование заказчика) — в доказательствах использованы только обезличенные номера строк и структура колонок.
- **Утечка через логи:** `parse()`/`splitRow` не логируют содержимое — ок. Рекомендация на будущее: не добавлять логирование содержимого students.csv.
- **Доступ к admin-базе не аутентифицирован** — он защищён только сборкой отдельного flavor (`applicationIdSuffix = ".admin"`). Это осознанная модель распространения (admin-сборка не публикуется для всех), но стоит зафиксировать: любой, кто получил admin-APK, видит все 1703 записи учащихся без входа. Вне рамок этого ревью, отмечено как риск.

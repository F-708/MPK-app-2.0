# Ревью: Виджеты (обновление, конфиг, все провайдеры)

_Дата: 2026-10-01. Область: widgets. Ревьюер: босс (лично), весь домен прочитан целиком._

## Резюме и вердикт

Код виджетов сам по себе написан аккуратно (кэши runBlocking-запросов, частичные обновления, корректные PendingIntent-коды). НО обновление целиком стоит на двух ненадёжных опорах: (1) точный будильник, который на Android 14+ по умолчанию НЕ разрешён, и (2) foreground-сервис, который OEM убивают. Отсюда жалоба «виджеты редко обновляются / глючат». Плюс виджет «СЕГОДНЯ» молча показывает ЧУЖОЙ день при провале синка (взаимодействие с SCH-01 — главным багом расписания).

## Критичные баги

### WID-01 [critical/bug] Виджет «СЕГОДНЯ» показывает последнюю дату из БД, а не сегодня
- **Файл**: `widget/NowNextWidgetProvider.kt:193-222` (`WidgetData.todayLessons`).
- **Root cause**: выбираются уроки `getLessonsForDaySync(group, dow)` (по дню недели), затем фильтруется **последняя (max) dateString** — «latest», а НЕ «today == todayString». Если синк сегодняшнего дня провалился (SCH-01: сайт отдал 404 на все кандидаты), в БД последняя дата — прошлая неделя/месяц, и виджеты «СЕЙЧАС/ДАЛЬШЕ» и «СЕГОДНЯ • группа» показывают **расписание чужого дня** под заголовком «СЕГОДНЯ». Никакой индикации устаревания.
- **Сценарий**: 1 октября синк упал → в БД лежат уроки с dateString 24.09 (последний успешный) → dow совпал (среда) → виджет рисует «СЕГОДНЯ» из 24.09. Пользователь идёт не в тот кабинет. Это «виджеты глючат» в чистом виде.
- **Доказательство**: строки 204-211 — `maxOfOrNull { parseDotDate(dateString)?.timeInMillis }`, фильтрация по `== latestMillis`. Сравнения с сегодняшней датой нет нигде в функции.
- **Фикс** (root-cause, минимальный): в `todayLessons` фильтровать по `dateString == todayString ИЛИ dateString.isBlank()`. Если на сегодня данных нет → вернуть пустой список (виджет честно покажет «Уроков нет / обновите расписание»), НЕ чужой день. Опционально: подмешать в заголовок дату данных, если они не сегодняшние.

### WID-02 [critical/bug] Minute-тик держится на точном будильнике, который Android 14+ не даёт по умолчанию
- **Файл**: `widget/BellCountdownWidgetProvider.kt:446-471` (`WidgetAlarm.scheduleNext`), манифест:9 (`SCHEDULE_EXACT_ALARM`).
- **Root cause**: при `!canScheduleExactAlarms()` (дефолт для fresh-install на Android 14+) код тихо деградирует до `setAndAllowWhileIdle` — inexact-будильник в doze batch-ится с задержкой до 15+ минут. `updatePeriodMillis` у трёх виджетов = 0 (намеренно), у countdown = 30 мин. Итог: без FGS-сервиса (выключен по умолчанию, `PREF_ENABLED=false` в BellCountdownNotifier:66) минутные виджеты обновляются «когда система соизволит».
- **Второе отверстие**: `WidgetAlarmReceiver.onReceive` (строки 487-491) при включённом нотификаторе обновляет ТОЛЬКО NowNext, полагаясь что BellCountdown уже обновил живой BellTimerService. Если сервис убит OEM (Xiaomi/Samsung battery saver убивают specialUse-FGS) — countdown-виджет встаёт до следующего неточного будильника.
- **Фикс**:
  1. В ресивере при `isEnabled` всё равно обновлять countdown, если `!BellTimerService.isRunning` (проверка флага уже есть — одна строка).
  2. `updatePeriodMillis=0` у NowNext/Today/Bells — система их вообще не будит; минутный тик для них только из будильника/сервиса. Поднять у Today/Bells до 1800000 (раз в полчаса система сама дёрнет onUpdate — бесплатная страховка; они не «мигают», т.к. меняются раз в урок).
  3. Экран/диалог «включите точные будильники» (deep-link `ACTION_REQUEST_SCHEDULE_EXACT_ALARM`) при `!canScheduleExactAlarms()` — без этого пользователь не понимает, почему виджет врёт.
  4. WorkManager-watchdog (15 мин): виджеты на экране && сервис должен работать && !isRunning → перезапуск. MpkWorkManagerHelper уже существует — добавить второй worker или ветку в ScheduleCheckWorker.

## Баги «через раз» / плавающие

### WID-03 [high/bug] Воркер «расписание на завтра» сдаётся на весь день после одного провала
- **Файл**: `worker/ScheduleCheckWorker.kt:138-141`.
- **Root cause**: `syncScheduleForDate` вернул пустой список (при SCH-01 это НОРМА — документ не найден по URL-кандидатам) → `checkedKey=true` → до конца target-даты воркер больше не пытается. Уведомление «вышло расписание на завтра» не придёт НИКОГДА, хотя документ появится на сайте через час.
- **Доказательство**: ветка `else` на 138: «Документ получен, но группа в нём не нашлась» — но `syncScheduleForDate` (ScheduleRepository:246-275) при `documentFound=false` возвращает `success(mine=empty)` — воркер НЕ отличает «документа нет» от «документ есть, группы нет».
- **Фикс**: `checkedKey` ставить только когда документ РЕАЛЬНО был найден (протащить `documentFound` из репозитория в результат, либо `Result.failure` при documentFound=false). После фикса SCH-01 проблема сузится, но различение «нет сайта/нет документа/нет группы» всё равно нужно.

### WID-04 [medium/bug] `lastGroupLessonForToday` кэшируется по минуте — кэш бесполезен
- **Файл**: `widget/BellCountdownWidgetProvider.kt:216-217` — ключ `"$group|$dow|$todayString|HH:mm"`.
- **Root cause**: «последний урок группы сегодня» не меняется в течение дня, но ключ включает минуты → кэш промахивается каждую минуту → `runBlocking`+Room-запрос 1440 раз/день при живом сервисе. Батарея. (Дубль BEL-04 — чинить одним движением: убрать `HH:mm` из ключа.)

### WID-05 [medium/bug] После переименования пакета старые виджеты пользователей мертвы
- **Контекст**: пакет переименован com.example→com.politex (2026-09-23), память проекта: «виджеты у пользователей после этого надо пересоздавать».
- **Root cause**: AppWidgetHost лаунчера держит провайдер по старому ComponentName; после обновления приложения старый провайдер исчезает → виджет показывает «проблему» и не обновляется. Плюс `SharedPreferences` живут, но `appWidgetId` у пересозданного виджета новый — настройки стиля/режима, привязанные к старому id (`countdown_mode_<id>`, `widget_style_<id>`), теряются.
- **Фикс**: одноразовая миграция при старте приложения: если в prefs есть записи `widget_style_<oldId>` и нет ни одного живого id — скопировать настройки на текущие id (или хранить дефолт-настройку «последний использованный стиль» и применять к новым id). Документировать в release notes «пересоздайте виджеты».

## Архитектура и ООП

- `WidgetStyle.load/save/remove` и `CountdownMode.load/save/remove` — дублирующий код prefs-обёрток (2×3 одинаковых функции). Мелочь, но просится обобщение `enumPref<T>(prefix, default)`.
- dow-конвертация Calendar→1..7 продублирована: WidgetData.dayOfWeek, Provider.buildViews:248, Provider.lastGroupLessonForToday:207, Notifier×2, ScheduleCheckWorker×2, CollegeBellSchedule.getCurrentSlot. **7 копий одной логики** — вынести в один `dowOf(Calendar)` (уже есть `MpkScheduleParser.dowOfCalendar` — переиспользовать его, в 01-отчёте то же замечание).
- `WidgetOptions.showRoom` — ок. Конфиг-активити (305 строк) не читал целиком — там вероятен дубль UI-стилей, проверить при правках.

## 1. Диагноз: топ-5 причин долготы

### 1.1. Проект лежит на HDD 5400 об/мин — все gradle-операции упираются в диск
**Измерено:** `D:` = диск 0 = **WDC WD20EARS-00J2GB0** (2 ТБ, медленный SATA-HDD; «Unspecified» = HDD без TRIM/SSD-признаков).
`C:` = Kingston NVMe SSD. Sequential-чтение D: ~**94 МБ/с** (копия файла 193 МБ D:→C:, 2.1с). Для сравнения C:→C: ~554+ МБ/с.
Главное — не sequential, а random I/O: у HDD ~100 IOPS, у NVMe в 100–1000 раз больше. Gradle-билд — это тысячи мелких
операций: хэширование сорссетов (up-to-date checks), журналы `.gradle/` (62 МБ), запись `app/build` (**951 МБ**),
git-операции (pack 110 МБ). Всё это на HDD.
**Усугубление:** на том же D: сегодня параллельно работал второй gradle-проект `D:\Minecraft\Mods\WMT`
(демон Gradle 8.10, PID 199228, с 17:55; тяжёлые chunkgen-логи 16:48–20:21 в `%TEMP%\opencode\wmt-*.log`) —
два проекта делят одну медленную шпиндельную головку.
**Вклад в долготу (оценка):** +50–100% к каждому билду относительно SATA/NVMe SSD. Инкрементальная компиляция
main-сорсета (40 004 LOC, 169 файлов) замерена в **2м41с** — для тёплого инкрементала на SSD это типично 40–80с (оценка).

## 2. Немедленные действия (применяет менеджер)

Правки ниже идентичны вносятся **в оба репо** (public синхронизируется копированием корневых build-файлов —
конфиги должны оставаться близкими, иначе кэш/поведение разъезжаются).

### 2.1. `app/build.gradle.kts` — параметры тестовых задач (оба репо)
Добавить в конец файла:
```kotlin
// Скорость юнит-сьета: параллельные форки + heap под Robolectric/Compose.
tasks.withType<Test>().configureEach {
  maxHeapSize = "2g"
  maxParallelForks = 2
}
```
- Эффект (оценка): полный сьют 1м42с → ~1м00–1м15с; меньше GC-пауз в Robolectric-тестах.
- Риск для CI: низкий. ubuntu-latest = 4 vCPU / 16 ГБ — 2 форка по 2 ГБ влезают. Локально при одновременно
  работающих агентах форки усилят конкуренцию за CPU/диск — поэтому правило «один gradle на каталог» (п.3.1) важнее.
- НЕ ставить maxParallelForks>2–3: каждый форк заново инициализирует Robolectric-sandbox (+15–25с) и ест heap.

### 2.2. Единый SDK для Robolectric — один sandbox вместо двух
Создать `app/src/test/resources/robolectric.properties` (оба репо):
```properties
sdk=35
```
- Классы без `@Config` перестанут молча идти на targetSdk=36 → останется один sandbox (SDK35) на форк:
  экономия ~10–20с на каждый прогон сьета + одна android-all jar в памяти вместо двух.
- Второй шаг (отдельная волна агента, не срочно): снять `sdk = [35]` из 39 `@Config(...)` (qualifiers оставить) —
  чтобы источник правды был один. Риск: минимальный (тесты и так писались под 35).
- Риск для CI: нулевой (jars уже в кэше, в CI скачается один вместо двух — даже быстрее).

### 2.3. `gradle.properties` — точечно (оба репо, файлы должны остаться идентичными)
Текущие настройки в целом здоровы (cc+caching+parallel включены). Менять только это:
```properties
# было: org.gradle.jvmargs=-Xmx4g -Dfile.encoding=UTF-8
org.gradle.jvmargs=-Xmx5g -XX:MaxMetaspaceSize=1g -Dfile.encoding=UTF-8
```
- Эффект: запас под in-process kotlinc на полном recompile (стратегия in-process не трогать — это осознанный фикс
  «Could not connect to Kotlin compile daemon»).
- Риск для CI: низкий (16 ГБ раннер, 5 ГБ демон + 2×2 ГБ форка — влезают).
- `org.gradle.workers.max=4` **оставить** (совпадает с 4 vCPU CI; локально можно переопределять в CLI:
  `-Dorg.gradle.workers.max=6` только для локальных менеджеровских прогонов, в файл не писать).
- Опциональный микро-флаг для точечных прогонов (все версии pinned, сеть не нужна): `--offline` —
  экономит секунды на проверках репозиториев. Не применять к первому билду после добавления зависимостей.

## 3. Правила процесса для менеджера

### 3.1. Конкурентность gradle: **1 сборка на один проект-каталог** (главное правило)
- Gradle-билды в одном каталоге сериализуются локами; параллельный запуск поднимает ВТОРОЙ демон (подтверждено:
  два демона 9.3.1 сегодня) и удваивает wall time обоих.
- Практически: одновременно gradle гоняет **один** агент. Второй в это время пишет код/читает/планирует, но НЕ запускает gradlew.
  Варианты координации: (а) менеджер явно раздаёт «окна» на gradle-прогоны; (б) агенты пользуют mutex-файл
  (`.gradle-lock`: создал атомарно → гоняешь; не смог → ждёшь/пишешь код); (в) worktree на агента (п.5.1) — снимает ограничение.
- Если нужен настоящий параллелизм агентов с прогонами — только worktrees (см. 5.1), на одном SSD.

### 3.2. Протокол волны (порядок гейтов)
1. Волна агентов (каждый сдаёт ТОЛЬКО с зелёной компиляцией своих файлов — см. блок 4).
2. **Checkpoint-компиляция сразу после волны, до чтения отчётов** (правило уже есть в mpk-build — соблюдать):
   `:app:compileStandardDebugKotlin` + `:app:compileStandardDebugUnitTestKotlin`.
   Красная компиляция → точечный микро-фикс-раунд на виновника (не перезапуск всей волны).
3. Полный сьют: `run-tests.sh` (~1м40с; с правками 2.1 — ~1м).
4. **Roborazzi — только по условию** (см. 3.3).
5. Коммит в main.
6. Sync → public → **pub-гейт lite** (см. 3.4) → push.
7. CI public (ci.yml) гоняет полный сьют сам — следить за runs, а не дублировать локально.

### 3.3. Когда запускать Roborazzi record
`run-robo.sh` = повторный полный прогон всех 1579 тестов + запись. Запускать **только** если diff волны затронул:
`app/src/main/java/com/politex/ui/**`, `.../widget/**`, `res/drawable*`, `res/layout*`, `res/values*/themes|colors|styles`,
или promo-shot тесты (`promo/PromoShotsTest`, `CollegeLogoShotTest`, `UpdateShotsTest`, `teacher/TeacherShotsTest`).
Иначе — пропуск (экономия ~2 мин/волна). Это совпадает с правилом mpk-build («после ЛЮБЫХ визуальных правок») —
уточнение в том, что «любые» = из списка выше, а не каждая волна.

### 3.4. Public-гейт: lite вместо полного (экономия ~4 мин/волна)
После sync в public локально достаточно (~1–1.5 мин):
```bash
./gradlew :app:compileStandardDebugKotlin :app:compileStandardDebugUnitTestKotlin --console=plain
./gradlew :app:testStandardDebugUnitTest --tests "com.politex.UiRenderSmokeTest" --tests "com.politex.ContentStartupCheckTest" --console=plain
```
Полный сьют всё равно выполнит **ci.yml при push в main** и **release.yml при теге** — двойная локальная страховка
избыточна. Полный `pub-tests.sh` оставлять для: (а) перед постановкой тега, (б) после изменения фильтров sync
(исключения admin/teacher/promo/PII), (в) если CI на main упал.
Риск: красный CI в public вместо зелёного локального прогона — приемлемо, т.к. идентичный код только что прошёл
полный сьют в main-репо; главный риск sync (недоложили файл) ловится compile-гейтом lite.

### 3.5. Фикс-раунды
- Правило сдачи «дерево зелёным» (блок 4) сокращает причину «чужая ошибка компиляции» на порядок.
- Если агент всё же сдал blocked-статус: менеджер сам гоняет checkpoint-компиляцию, по тексту ошибки определяет
  владельца файла, точечный фикс-агент на 1 задачу — не перезапускать волну целиком.
- `LiveNetworkSmokeTest`: держать существующее правило «1 ретрай, known-flaky — pass». Не включать ретраи в
  автоматический цикл больше одного раза.

### 3.6. Тяжёлые сборки
`assembleAdminRelease` (8 мин) / `assembleDebug` (4 мин) — только по явной нужде (релиз, проверка R8/students.csv-гейт),
не в волновом цикле. Совмещать с релиз-днём, не с волнами.

## 4. Правила для рабочих агентов (блок для вставки в промпты)

```
GRADLE-ДИСЦИПЛИНА (обязательно):
1. Один gradle на каталог: перед запуском gradlew убедись, что другой сборки не идёт (нет свежего java-процесса
   с растущим CPU / менеджер не объявил окно). Если gradle занят — пиши код, жди окна. НЕ запускай вторую сборку.
2. Батчи прогоны: все свои тест-классы — ОДНИМ вызовом:
   sh ./gradlew :app:testStandardDebugUnitTest --tests "com.politex.Foo*" --tests "com.politex.BarTest" --console=plain
3. Сдаёшь задачу ТОЛЬКО если у тебя зелёные (по порядку):
   :app:compileStandardDebugKotlin → :app:compileStandardDebugUnitTestKotlin → твои --tests.
   Компиляция падает на ЧУЖИХ файлах — не чини чужое, не сдавай «тесты не прогнаны» молча:
   репорт менеджеру с точной ошибкой и файлом, статус BLOCKED-BY:<файл>.
4. Держи дерево компилируемым: не оставляй полунаписанных файлов между gradle-запусками —
   твой WIP ломает прогоны других агентов (компилируется ВЕСЬ сорсет).
```

## 6. Чего НЕ делать

1. **Не чистить `build/`, `.gradle/`, `~\.gradle\caches` в рабочий день.** Холодный старт = полная перекомпиляция
   (~4–6 мин) + re-store cc + переописание build-cache. (Скилл mpk-build сам предупреждает про это.)
2. **Не выключать `org.gradle.configuration-cache` и `org.gradle.caching`** — они работают и уже экономят
   (cc-reuse ~4с overhead замерен; build-cache-1 726 МБ используется).
3. **Не менять `kotlin.compiler.execution.strategy=in-process`** на daemon/out-of-process — это осознанный фикс
   ошибки «Could not connect to Kotlin compile daemon» на этой машине.
4. **Не ставить `maxParallelForks` > 2–3** для Robolectric: каждый форк платит sandbox-инициализацию и 2 ГБ heap;
   на 6 ядрах при параллельных агентах начнётся трешинг и рост флакерности.
5. **Не запускать два gradle в одном каталоге «чтобы быстрее»** — локи сериализуют их, а второй демон съест RAM/CPU
   (наблюдали сегодня).
6. **Не гонять `recordRoborazzi` «на всякий случай»** — это полный повторный сьют (~2 мин); verify-режима в проекте
   нет, скриншоты — промо-артефакты.
7. **Не удалять `LiveNetworkSmokeTest`** — это фактическая живая приёмка URL-резолвера; только правило ретрая.
8. **Не разъезжаться конфигами main/public** (gradle.properties, общие части build.gradle.kts) — sync копирует
   корневые build-файлы; расхождение = непредсказуемые recompile и разные результаты гейтов.
9. **Не переносить проект на C:** — 25 ГБ свободно, там уже `~\.gradle` (11.4 ГБ) и система; целевой диск E: (88 ГБ).
10. **Не включать AV/Defender без исключений** из п.2.5 — получите +20–50% к каждому билду (оценка).
11. **Не понижать `org.gradle.workers.max` ниже 4** и не зашивать локальные значения (>4) в общий файл — он
   синхронизируется в public и влияет на CI (4 vCPU).

## ✅ Принято

| Идея | Уточнения |
|---|---|
| **Виджет «следующая пара»** | Второй виджет, включается отдельно. Дополняет «до звонка»: дисциплина, кабинет, время |
| **Бекап настроек и заданий в файл** | Обязательно обратная совместимость — ничего не должно потеряться |
| **Архив расписаний за прошлые дни** | С сайта они исчезают, а под рукой иметь полезно |
| **Офлайн-кэш карточек преподавателей** | Фото и данные локально, чтобы не подгружать каждый раз |
| **Индикатор «данные от даты»** | Ненавязчивая пометка, что где-то что-то произошло. Плюс продублировать в дебаг |
| **Темы приложения** (не только виджета) | Цвета менять можно, но стиль остаётся колледжа (как на сайте) |
| **Карта корпусов и поиск кабинета** | Долгая разработка, но хочу. См. отдельный раздел ниже |
| **Масштаб интерфейса в настройках** | Требует тщательного рефактора каждой страницы — поля не должны съедаться |
| **Свой словарь сокращений** | Переименовывать предметы под себя, сохранять в кэш |
| **Перестановка вкладок** | Звонки/Задания можно перенести в «Другое». «Другое» остаётся всегда |
| **Числитель / знаменатель недели** | Только если ненавязчиво и незаметно |

## 🗺️ Карта корпусов (отложено, но задокументировано)

Замысел заказчика дословно: есть PNG-сканы пожарных планов этажей, на них
подписаны кабинеты — по ним и ориентируются.

Сценарий: во вкладке «Расписание» нажать на номер кабинета → открывается
интерактивное окно с картой → один раз проигрывается короткая анимация
(приближение → отдаление, «раскрывается этаж») → камера останавливается на
нужном кабинете → кабинет подсвечивается синим и слегка пульсирует. Закрыл и
открыл снова — снова короткая анимация, заканчивается на кабинете. Анимация
короткая, чтобы не грузить устройство.

**Что нужно от заказчика:** сами PNG-планы и привязка кабинет → этаж → корпус →
координаты на картинке.

## 🐙 GitHub как хостинг расписания — ИЗУЧИТЬ, потом обсуждать

Идея нравится, но сначала полное исследование. Вопросы заказчика:

1. Сколько GitHub Actions даётся бесплатно для **публичных** репозиториев?
2. Как сделать синхронизацию по расписанию и насколько часто реально (раз в минуту / 5 минут)?
3. Что будет, если GitHub ляжет или кончатся лимиты — какие запасные варианты хостинга?
4. Приложение публичное → репозиторий будет **отдельный новый**, где только
   рабочая версия, обновления и оповещения.

Функциональные требования, если делать:

- Расписание публикуется **в случайное время** (иногда поздний вечер, иногда утро),
  поэтому нужно часто пулить и проверять.
- Одновременные запросы всех телефонов — лишняя нагрузка на сайт колледжа.
  Один парсер на сервере → всем готовый JSON.
- При ручном обновлении пользователем — запрос в GitHub; но с откатом ~30 секунд,
  чтобы поток запросов от разных людей не долбил GitHub.
- Автоматическая проверка — раз в 5 минут (или чаще, если позволят лимиты).
- **Парсинг .doc с сайта остаётся запасным каналом** — если GitHub недоступен,
  приложение обязано само разобрать документ и работать.
- Уведомления о появлении нового расписания.

Данные:

- **Учащиеся — только в admin-версии. На GitHub их быть не должно.**
- Преподаватели — в основном уже лежат в приложении на устройствах. Нужно
  посчитать нагрузку и найти баланс: что тянуть с сайта, что с GitHub.

# Правки к 2.12

Разбор текущей сборки заказчиком.

1. **Клик по преподавателю незаметен.** Он работает, но неочевиден — нужен
   визуальный признак, что по преподавателю можно нажать.
2. **При разделении группы на подгруппы преподаватели не нажимаются.** Баг,
   исправить.
3. **Фотографии преподавателей обрезаны (1:1) — нельзя обрезать.** Выводить
   полное фото с сайта. Примеры: Бирюк В. В., Зыбин О. Л. — обрезаны лица.
4. **В карточке преподавателя слишком много переключателей** (Контакты,
   О преподавателе, Дисциплины, У вашей группы, Расписание) — мало функционала
   на каждый. Слить в **две вкладки**:
   - **«О преподавателе»**: фото, должность, подразделение, стаж, квалификация,
     дисциплины, контакты (**блок контактов убрать целиком, если контактов нет**),
     внизу — «у вашей группы» (что ведёт у группы).
   - **«Расписание»**: всё, что относится к расписанию (сегодня / завтра / календарь).
5. **Уведомление**: убрать **золотую тему** — выглядит плохо.
6. **Стиль уведомления «с полосой прогресса»**: название «до звонка 5 минут» и
   описание тоже «5 минут» — дублирование. Оставить название, описание убрать,
   полосу оставить.
7. **База учащихся: прокол с курсом.** Пример — Абражевич Елизавета
   Владиславовна, группа 41D, в базе указан 4 курс, хотя специальность учит
   3 курса. Проверить синергию «специальность ↔ число курсов» и убедиться, что
   таких записей больше нет: нельзя отправлять человека на несуществующий курс.
8. **Первых уроков может не быть** (нет 1-го, 2-го, 3-го, 4-го). Сейчас это
   выглядит дыркой. Нужна аккуратная пометка, что урока нет.

# Новые задумки

## 🔑 Активация приложения по токену

**Зачем.** Приложение хочется раздать одногруппникам, но есть страх: разошлют сырую
версию дальше, ей начнут пользоваться, а автор не сможет ничего обновить.

**Как задумано.**

- В обычном «Моём Политехе» при входе обязательно спрашивается **токен разблокировки**.
  Без него приложение не работает.
- Токен **динамический**: зависит от текущего времени/даты и общих для всех телефонов
  условий. Значит, он вычисляется одинаково на любом устройстве — отдельный сервер не нужен.
- В admin-версии — отдельная вкладка **«Как подключить приложение»**, которая
  генерирует код и **QR-код**.
- В обычной версии токен вводят руками **или сканируют QR** с admin-приложения.
- Стойкость: «чтобы не было легко расшифровать», но без паранойи — разбирать APK
  никто не будет.

**Открытые вопросы (решить перед реализацией).**

1. Окно действия токена: сколько он живёт — минута, пять, сутки? Чем короче, тем
   сложнее делиться, но тем чаще придётся вводить заново.
2. Что делать, если код всё-таки утёк: как «отозвать» уже активированные устройства?
   Вариант — привязка к периоду, тогда старый код сам перестаёт работать.
3. Терять ли активацию при обновлении приложения и при переустановке.
4. Нужен ли офлайн-режим для уже активированного устройства (да, скорее всего).

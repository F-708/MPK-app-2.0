## 0. Что вообще предлагается, на пальцах

Заказчик спрашивает: можно ли **не платить за сервер** и держать расписание колледжа на GitHub?

Да, можно. Схема такая:

```
Сайт колледжа (.doc/.xls)
        │
        │  1 раз в N минут GitHub сам запускает скрипт (GitHub Actions)
        ▼
Скрипт парсит расписание → собирает schedule.json + teachers.json
        │
        │  2. коммитит файлы в репозиторий (только если содержимое изменилось)
        ▼
Публичный репозиторий на GitHub
        │
        │  3. отдаёт файл приложению через CDN (raw.githubusercontent.com)
        ▼
Android-приложение «Мой Политех»
```

Три независимых сервиса, каждый со своими лимитами:

| Звено | Что делает | Кто платит |
|---|---|---|
| **GitHub Actions** | запускает парсер по расписанию | GitHub, бесплатно |
| **Хранилище** | публичный git-репозиторий с JSON | GitHub, бесплатно |
| **Раздача (CDN)** | отдаёт JSON телефону студента | GitHub / Cloudflare / jsDelivr |

**Главный вывод одной строкой:** упирается всё не в деньги (везде 0 ₽), а в
**надёжность cron-расписания GitHub Actions** и в **кэш CDN на 5 минут**.
Оба ограничения обходимы, см. разделы 6 и 8.

## 1. GitHub Actions для публичных репозиториев

### 1.1. Сколько минут бесплатно

Официальная формулировка документации GitHub (перевод дословный):

> «Использование GitHub Actions **бесплатно** для **self-hosted раннеров** и для
> **публичных репозиториев**, использующих стандартные раннеры, размещённые на GitHub.»

То есть **да, для публичного репозитория минуты неограниченны и не тарифицируются.**
Это не «2000 минут и потом плати», а именно «free» без счётчика.

Важные оговорки:

| Оговорка | Последствие |
|---|---|
| **Larger runners** (усиленные машины) платные **всегда**, даже в публичном репо | Не используем их — стандартного Ubuntu-раннера хватает с запасом |
| Для **приватных** репо минуты лимитированы | Free: 2 000 мин/мес, Pro: 3 000, Team: 3 000, Enterprise Cloud: 50 000 |
| Каждая задача округляется **вверх до целой минуты** | Задача на 61 секунду спишет 2 минуты (в публичном репо — неважно) |
| Перезапуск (re-run) считается как новый запуск | Неважно для публичного репо |

**Вывод:** парсер расписания, который работает 30–60 секунд, в публичном репозитории
можно запускать хоть каждые 5 минут круглосуточно — счёт за это не придёт никогда.

### 1.2. Ограничения по частоте запуска (cron)

| Параметр | Значение | Источник |
|---|---|---|
| **Минимальный интервал cron** | **1 раз в 5 минут** (`*/5 * * * *`) | документация GitHub (см. примечание ниже) |
| Часовой пояс | **только UTC** (МСК = UTC+3) | docs |
| Ветка | только **default branch** (main), с других веток не сработает | docs |
| Retry / пропуск | если запуск пропущен — **GitHub его не «догоняет»**, прогноз на будущее | docs (косвенно) |
| Автоотключение | В **публичном** репо расписание **автоматически выключается после 60 дней без активности** в репозитории | docs, дословно |
| Лимит на очередь | 500 запусков в 10 секунд на репозиторий; 1500 событий в 10 секунд на репозиторий | docs |
| Параллельные задачи (Free) | 20 одновременных задач на аккаунт | docs |

> **Примечание про 5 минут.** В текущей редакции документации для Free/Pro фраза
> «The shortest interval you can run scheduled workflows is once every 5 minutes»
> из текста убрана, но она **до сих пор есть в документации GitHub Enterprise Server 3.17**
> и поведение платформы не изменилось. Практический вывод: ставить cron чаще, чем `*/5`,
> бессмысленно — GitHub всё равно запустит не чаще раза в 5 минут (и не гарантирует
> даже этого, см. раздел 2).

**Пример рабочего cron:**

```yaml
on:
  schedule:
    - cron: "7,22,37,52 * * * *"   # каждые 15 минут, со сдвигом от :00
  workflow_dispatch:                # + кнопка ручного запуска в UI
```

Обратите внимание: минуты `7,22,37,52`, а не `0,15,30,45`. Причина — в разделе 2.

## 2. Насколько ненадёжен `schedule:` — официальное подтверждение

Это самое слабое место всей схемы. GitHub **сам, в документации**, признаёт проблему.
Дословная цитата (перевод):

> «Событие `schedule` **может быть отложено** в периоды высокой нагрузки на запуски
> workflow. Периоды высокой нагрузки включают **начало каждого часа**. Если нагрузка
> достаточно высока, **некоторые задачи в очереди могут быть отброшены** (dropped).
> Чтобы снизить вероятность задержки, запланируйте workflow на другое время внутри часа.»

Обратите внимание на три вещи из одной цитаты:

1. Задержки — **официально признаны**, это не баг вашего конфига.
2. «dropped» — запуск может быть **выброшен совсем**, без уведомления.
3. GitHub прямо советует **уходить от начала часа** (то есть от `0 * * * *` и от `0,15,30,45`).

### 2.1. Насколько именно задерживается — реальные числа

Официальной цифры «сколько минут» GitHub не публикует — гарантий по времени нет вообще
(SLA на запуск cron отсутствует). По публичным отчётам разработчиков:

| Источник | Наблюдаемая задержка |
|---|---|
| Stack Overflow, вопрос 79534419 (cron каждые 10 мин) | запуски приходят через 10, 20 и **30 минут** |
| GitHub Community Discussion #206287 | стабильные **5–45 минут** задержки, затем «плавающие» времена |
| DEV Community (разбор инцидента) | **55–65 минут** опоздания, иногда запуск не происходит вовсе |
| DevActivity (аналитика по инциденту ~26.08.2026) | задержки **3–10 часов**, часть запусков вообще не создана |
| GitHub Community Discussion #203822 | расписание не сработало **ни разу**, при этом `workflow_dispatch` работал |

**Что это значит для расписания колледжа.** Расписание меняется раз в сутки (иногда —
экстренно, «заменили пару»). Задержка cron в 30 минут **никого не сломает**: студент
всё равно увидит обновление. Катастрофа была бы, если бы мы обещали «расписание
обновится ровно в 07:00». Мы этого не обещаем — и не должны.

**Критично для дизайна:** раз запуск может быть **выброшен молча**, нельзя строить
схему так, будто расписание гарантированно обновляется раз в сутки. Нужен «храповик»:
расписание лежит в приложении локально, а обновление — улучшение, а не условие работы.
См. раздел 8.

## 3. GitHub API и `raw.githubusercontent.com`

Это два **разных** сервиса с **разными** лимитами. Их постоянно путают.

| | `api.github.com` (REST API) | `raw.githubusercontent.com` (CDN) |
|---|---|---|
| Для чего | метаданные, список файлов, дата коммита | **просто отдать содержимое файла** |
| Лимит без токена | **60 запросов/час на IP** | **числового лимита в документации нет** |
| Лимит с токеном | 5 000 запросов/час | — |
| Лимит `GITHUB_TOKEN` в Actions | 1 000 запросов/час на репозиторий | — |
| Заголовки `x-ratelimit-*` | есть | **отсутствуют** |
| Нужен ли токен | для 60/час — нет | нет вообще |

### 3.1. Относится ли «60 запросов/час» к raw?

**Официальный ответ: в документации GitHub лимит 60/час описан для REST API
(`api.github.com`). Для `raw.githubusercontent.com` никакого числового лимита
в документации не заявлено.**

Проверено вживую 16.09.2026:

```
$ curl -I https://raw.githubusercontent.com/github/docs/main/README.md
HTTP/1.1 200 OK
Cache-Control: max-age=300          <- кэш 5 минут
ETag: "3909856f30420d..."           <- сильный ETag, годится для If-None-Match
Vary: Authorization, Accept-Encoding
X-Cache: HIT
X-Served-By: cache-fra-eddf8230065-FRA
Via: 1.1 varnish                    <- отдаёт Fastly (CDN), не приложение GitHub
Expires: Wed, 16 Sep 2026 18:24:38 GMT
```
Заголовков `x-ratelimit-limit` / `x-ratelimit-remaining` в ответе **нет** —
в отличие от `api.github.com`, где они есть:

```
$ curl -I https://api.github.com/repos/github/docs
X-RateLimit-Limit: 60
X-RateLimit-Remaining: 53
X-RateLimit-Resource: core
```

И тест «в лоб» — 60 быстрых запросов к raw подряд:

```
$ for i in $(seq 1 60); do curl -o /dev/null -w "%{http_code}\n" \
    "https://raw.githubusercontent.com/github/docs/main/README.md?cb=$i"; done | sort | uniq -c
     60 200
```
Все 60 — успешные, ни одного 429. (Тест маленький, 60 запросов не могли спровоцировать
защиту от абьюза, но факт отсутствия счётчика подтверждают заголовки.)

**Но осторожно:** отсутствие лимита в документации ≠ «можно качать бесконечно».
Юридически работает **пункт 9 Acceptable Use Policies — «Excessive Bandwidth Use»**:

> «Если мы определим, что использование вами полосы пропускания значительно превышает
> использование другими пользователями аналогичных функций, мы оставляем за собой право
> приостановить ваш аккаунт, ограничить хостинг файлов или иным образом ограничить
> вашу активность… а также — после предварительного уведомления — **удалить репозитории**,
> которые, по нашему мнению, создают чрезмерную нагрузку на нашу инфраструктуру.»

Перевод на человеческий: **один JSON-файл расписания, который скачивают 500 студентов
несколько раз в день, — это норма.** Если бы мы гоняли через raw видео или
многомегабайтные архивы — GitHub бы вмешался. Текст расписания — десятки/сотни
килобайт, это ничтожно.

### 3.2. ETag / If-None-Match и ответ 304

**Что такое ETag простыми словами.** Это «отпечаток версии файла» — строка, которую
сервер выдаёт вместе с файлом. Телефон запоминает отпечаток и в следующий раз
спрашивает: «у меня версия с таким отпечатком, она ещё актуальна?» Если да —
сервер отвечает **`304 Not Modified`** и **не присылает тело файла**.

Проверено вживую:

```
$ ETAG=$(curl -I .../README.md | grep -i ^etag: | cut -d' ' -f2)
$ curl -H "If-None-Match: $ETAG" .../README.md
HTTP/1.1 304 Not Modified
ETag: "3909856f30420d..."
Cache-Control: max-age=300
```

Работает. Экономия: вместо 200 КБ по мобильному интернету — пара сотен байт заголовков.

**А даёт ли 304 право не снижать лимит?** Формально — да, но только для REST API.
Дословно из документации:

> «Условный запрос **не засчитывается** в ваш primary rate limit, если вернулся ответ
> `304`, **и запрос был сделан с корректной авторизацией через заголовок `Authorization`».**

Два важных следствия:

1. Льгота по 304 привязана к **авторизованному** запросу к `api.github.com`. Для
   неавторизованного запроса (тех самых 60/час) официальной льготы на 304 нет.
2. **В схеме с raw нам это не нужно вообще** — у raw счётчика нет, экономить нечего.
   ETag в схеме с raw нужен ради **трафика и батареи телефона**, а не ради лимита.

> Ещё нюанс, который стоит знать: `raw.githubusercontent.com` **игнорирует
> `If-Modified-Since`** и всегда отвечает 200, но **корректно понимает `If-None-Match`
> с ETag** и отдаёт 304. Это подтверждено сторонним публичным разбором
> (PR esphome#16020), где именно на этом «сгорали» повторные скачивания. Использовать
> надо **ETag**, а не Last-Modified.

### 3.3. Кэш CDN у raw — сколько живёт и как обойти

Из живого ответа выше: **`Cache-Control: max-age=300` = 5 минут.**

Что это значит практически:

| Ситуация | Что увидит телефон |
|---|---|
| Файл в кэше CDN, вы только что его запушили | **до 5 минут** старую версию |
| Запрос с `?cb=<random>` | параметры строки запроса **не обходят** кэш Fastly (проверено: `?cb=1..60` отдавались из кэша мгновенно, `X-Cache: HIT`) |
| Ответ 304 | сбрасывает кэш нельзя, но и трафик не тратится |

**Способ обойти кэш — единственный надёжный:** обратиться по **конкретному коммиту**
(или указать в имени файла хеш содержимого):

```
# обычная ссылка: кэш 5 минут
https://raw.githubusercontent.com/<user>/<repo>/main/schedule.json

# ссылка на конкретный коммит: содержимое неизменяемо => кэш не мешает
https://raw.githubusercontent.com/<user>/<repo>/<commit-sha>/schedule.json
```

Но для этого приложению нужно **сначала узнать commit-sha** — а это уже запрос к
`api.github.com` (60/час на IP, и общий NAT колледжа — реальный риск). Поэтому
**на практике для мобильного приложения правильнее смириться с 5-минутным кэшем raw.**

**5 минут опоздания для расписания — не проблема.** Проблема была бы, если бы мы
использовали расписание как «команды в реальном времени». Мы так не делаем.

## 4. Альтернативы GitHub-раздаче

### 4.1. Сводная таблица

| Вариант | Бесплатно? | Лимиты | Карта? | Вердикт |
|---|---|---|---|---|
| **raw.githubusercontent.com** | да | числового лимита в доке нет; кэш 5 мин; AUP §9 про чрезмерный трафик | нет | ✅ **основной канал** |
| **GitHub Pages** | да (публичный репо) | 100 ГБ/мес трафика (soft), 10 сборок/час (soft), сайт ≤ 1 ГБ, деплой ≤ 10 мин, возможен 429 | нет | ⚠️ избыточно; но **годная резервная площадка** |
| **Cloudflare Workers** | да, Free | **100 000 запросов/сутки**, CPU 10 мс, 5 cron-триггеров на аккаунт, cron — хоть каждую минуту | нет | ✅ **лучший «умный» вариант** |
| **Cloudflare Pages** | да, Free | **запросы к статике бесплатны и безлимитны**, 500 сборок/мес, 25 МиБ на файл, 20 000 файлов | нет | ✅ отличный хостинг статики |
| **jsDelivr (поверх GitHub)** | да | «никаких лимитов пропускной способности»; файл ≤ 20 МБ (GitHub), пакет ≤ 150 МБ; HTML отдаётся как `text/plain` | нет | ⚠️ **кэш 12 часов для ветки** — не подходит для свежего расписания (см. 4.5) |
| **Firebase / Supabase** | частично | Free-тарифы есть, но требуют аккаунт и имеют свои лимиты | иногда | ➖ не нужно, усложняет |

### 4.2. GitHub Pages — актуальные лимиты (проверено в документации 16.09.2026)

> **Важно:** цифры 100 ГБ/мес и 10 сборок/час **актуальны и сейчас**.

| Лимит | Значение | Тип |
|---|---|---|
| Трафик сайта | **100 ГБ в месяц** | *soft* (мягкий) |
| Сборок в час | **10** | *soft*; **не применяется**, если сайт собирается через собственный GitHub Actions workflow |
| Размер опубликованного сайта | ≤ **1 ГБ** | — |
| Размер репозитория-исходника | рекомендовано ≤ 1 ГБ | рекомендация |
| Таймаут деплоя | 10 минут | — |
| Пользовательский/организационный сайт | **один на аккаунт** | — |
| Rate limit | возможен ответ **429** | — |

Слова «soft» означают: при превышении GitHub **не отрубает сайт сразу**, а пишет
вежливое письмо с предложением поставить перед сайтом сторонний CDN или
переехать. Плюс отдельно в доп. условиях: **Pages нельзя использовать как бесплатный
хостинг для коммерческого SaaS/интернет-магазина.** Расписание колледжа под это
ограничение не попадает.

Проверка арифметикой: 100 ГБ/мес ≈ 3,3 ГБ/сутки. Если `schedule.json` весит 200 КБ,
это ≈ **17 000 скачиваний в сутки** — примерно 3 000–5 000 активных студентов
с запасом. Для одного колледжа — хватает, но запас меньше, чем у raw.

**Когда Pages реально полезен:** как **резервный канал**. Если основной домен
недоступен, приложение переключается на `https://<user>.github.io/<repo>/schedule.json`.
Это другой хост — падает реже, чем конкретный сервис.

### 4.3. Cloudflare Workers (Free)

| Параметр | Free-тариф |
|---|---|
| Запросы | **100 000 в сутки**, сброс в 00:00 UTC |
| CPU-время | 10 мс на запрос |
| Память | 128 МБ |
| Cron-триггеры | **5 на аккаунт**; минимальный интервал — **1 минута** (можно `*/1 * * * *`) |
| Суточный лимит | общий для Workers + Pages Functions |
| Worker'ов на аккаунт | 100 |
| Размер Worker'а | 64 МиБ |
| Egress (трафик наружу) | **не тарифицируется** |

Платный тариф — от **$5/мес** (10 млн запросов включено). Для нашей задачи Free
хватает с гигантским запасом: 100 000 запросов/сутки при 200 КБ JSON — это
десятки тысяч студентов.

**Что даёт Worker, чего не даёт raw:**
- Своя логика: **свой ETag**, свой `Cache-Control`, отдача `304`, редиректы.
- Свой cron (каждую минуту, `*/1`) — **в обход ненадёжного `schedule:` GitHub Actions**.
- Можно **проксировать GitHub API с токеном** (5 000 запросов/час вместо 60) — токен
  спрятан на стороне Worker'а, в APK его нет.
- Единая точка входа: приложение стучится в один URL, а Worker сам решает, откуда брать данные.

**Чего Worker не даёт:** гарантий SLA на Free-тарифе тоже нет, и это ещё одна
внешняя зависимость (Cloudflare вместо GitHub).

**Про карту:** для Free-тарифа достаточно зарегистрировать аккаунт Cloudflare
(в документации по началу работы — только «Sign up for a Cloudflare account» и
установка Node.js, шаг с оплатой отсутствует). Рекомендую при первой регистрации
убедиться глазами, что не просят карту — это 2 минуты.

| Запросы к Functions | считаются в те же 100 000/сутки Workers Free |
| Сборки | **500 в месяц**, 1 одновременно |

| Кастомные домены | 100 на проект |
| Preview-деплои | без ограничений |

**Это самый «щедрый» вариант по трафику:** статика не считается вообще.
Можно подключить свой домен (например, `schedule.mpk-app.ru`) — и это будет выглядеть
как «настоящий сервис», а не как ссылка на GitHub.

### 4.5. jsDelivr — почему НЕ подходит как основной канал

jsDelivr — бесплатный CDN, который умеет отдавать файлы прямо из GitHub-репозитория:

```
https://cdn.jsdelivr.net/gh/<user>/<repo>@main/schedule.json
```

Заявлено: «никаких лимитов пропускной способности… полностью бесплатно».
Но есть **убийственная для нас деталь — кэширование**. Дословно из документации jsDelivr:

| Тип ссылки | Время кэша |
|---|---|
| Static versions и **commit hashes** | «практически навсегда» (заголовок 1 год + постоянное хранение в S3) |
| Version aliasing (в т.ч. `latest`) | **7 дней**, можно сбросить через purge API |
| **Ветки (например `@main`)** | **12 часов** |

Проверено вживую 16.09.2026:

```
$ curl -I https://cdn.jsdelivr.net/gh/github/docs@main/README.md
Cache-Control: public, max-age=604800, s-maxage=43200
x-jsd-version: main
x-jsd-version-type: branch
Age: 7902
```
`s-maxage=43200` = **12 часов на edge**. То есть при `@main` новая версия расписания
доедет до студента **через 12 часов**. Для расписания это неприемлемо.

Ссылка по commit-SHA кэшируется навсегда — но, как и в случае raw, нужен способ
узнать этот SHA (запрос к GitHub API).

**Остальные особенности jsDelivr:**
- Purge-API существует, но **доступ к нему выдаётся по письму на почту** (`d@jsdelivr.com`),
  и purge работает **только для валидных semver-релизов** (например `@1.2.0`), не для веток.
- Ограничения: пакет > 150 МБ или **один файл > 20 МБ (для GitHub)** не поддерживаются.
- HTML-файлы отдаются с `Content-Type: text/plain` (для безопасности). JSON это не касается.

**Итог: jsDelivr годится для версионированных релизов, но не для «свежего» расписания.**

## 5. Риски: блокировка, падение, превышение лимитов

### 5.1. Что если заблокируют аккаунт/репозиторий

| Сценарий | Вероятность | Что происходит | Как страхуемся |
|---|---|---|---|
| Репозиторий удалён/приватнут владельцем | низкая | приложение получает 404, расписание не обновляется | локальный кэш в приложении — последнее расписание остаётся |
| Жалоба DMCA на содержимое | очень низкая (расписание — не объект авторского права в этом смысле) | репозиторий временно недоступен | резервная копия в другом репо / Cloudflare |
| Нарушение AUP §9 (чрезмерный трафик) | низкая | сначала письмо, потом троттлинг, потом удаление репо | маленькие JSON-файлы, кэш CDN, ETag |
| Аккаунт заблокирован за нарушение ToS | очень низкая | отваливается всё: и Actions, и хостинг | **владение репозиторием на отдельном «техническом» аккаунте**, не на личном |
| Приватный репо случайно сделан приватным для чужого токена | — | парсер работает, приложение — 404 | мониторинг: heartbeat-проверка раз в сутки |

**Практический совет:** для расписания завести **отдельный GitHub-аккаунт** (или
отдельную организацию) — чтобы блокировка личного аккаунта разработчика не убила
приложение.

### 5.2. Что если GitHub упадёт

GitHub падает. Это факт, а не пессимизм. При этом:

- **`raw.githubusercontent.com` (Fastly CDN)** и **`api.github.com`** — разные
  инфраструктуры и падают **не одновременно**. Кэш Fastly живёт 5 минут и продолжает
  отдавать файлы, даже когда сам GitHub лежит.
- **GitHub Pages** — третья независимая площадка.
- **Cloudflare** — четвёртая, и она же решает проблему, если GitHub недоступен: Worker
  может отдавать **последнюю известную версию** JSON из своего KV-хранилища.

**Вывод: приложение обязано иметь локальную копию расписания.** Оно и так её имеет
(Room/SQLite). Синхронизация — это улучшение, а не условие работы. Тогда падение
любого из внешних сервисов студент просто не заметит.

### 5.3. Что конкретно происходит при превышении лимитов

| Лимит | Ответ | Что видит приложение |
|---|---|---|
| REST API 60/час без токена | **403** или **429**, `x-ratelimit-remaining: 0` | ошибку синхронизации; надо ждать `x-ratelimit-reset` |
| Secondary rate limit (частые параллельные запросы) | 403/429 + заголовок `Retry-After` | нужно подождать указанное число секунд |
| GitHub Actions limit | workflow отменяется | расписание просто не обновилось в этот раз |
| AUP (трафик) | письмо → троттлинг → удаление | данные перестают обновляться |
| Cloudflare Workers Free 100k/сутки | запросы сверх лимита получают ошибку | **только на следующие сутки** после сброса в 00:00 UTC |
| GitHub Pages 100 ГБ/мес (soft) | сначала письмо, при злоупотреблении — 429 | сайт может не отдаваться |

**Важное правило из документации:** «Продолжение запросов, пока вы под rate limit,
может привести к **бану вашей интеграции**». Поэтому при 429 приложение **обязано**
остановиться и уважить `Retry-After` / `x-ratelimit-reset`, а не долбить сервер.

## 6. Практика: как опрашивать репозиторий с телефона

### 6.1. Базовые правила

1. **Ходить на `raw.githubusercontent.com`, а не в API.** Счётчика нет, токен не нужен.
2. **Всегда слать `If-None-Match` с сохранённым ETag.** Неизменившийся файл → `304`
   → не тратится мобильный трафик и батарея.
3. **Не использовать `If-Modified-Since`** — raw его игнорирует.
4. **Показывать в UI `generated_at` из самого JSON**, а не время запроса. Кэш CDN
   5 минут означает, что «время запроса» может врать.
5. **Никаких параллельных запросов.** Документация GitHub прямо просит делать запросы
   последовательно (parallel — прямой путь к secondary rate limit).
6. **Экспоненциальный backoff** при любой ошибке: 1 с → 2 с → 4 с → 8 с, максимум
   ~5 минут, плюс уважение `Retry-After`.
7. **Никогда не удалять локальную копию при ошибке сети.** Ошибка загрузки ≠ «расписания нет».

### 6.2. Рекомендованные интервалы — с обоснованием

| Когда | Интервал | Почему именно так |
|---|---|---|
| **Обычный режим (приложение открыто)** | **не чаще 1 раза в 30 минут** | Кэш CDN = 5 мин, генерация на GitHub = раз в 15–30 мин. Опрос чаще 30 минут не даёт новой информации, только жжёт батарею |
| **При открытии экрана расписания** | **1 раз, но не чаще 1 раза в 10 минут** | Студент хочет «свежее сейчас». 10 минут — порог, ниже которого кэш CDN всё равно вернёт то же самое |
| **Push/обновление по кнопке** | без ограничений (ручное действие) | Пользователь сам инициировал, нагрузка ничтожна |
| **Фоновый опрос (WorkManager)** | **1 раз в 12 часов** | Достаточно, чтобы утреннее расписание было актуальным; работает даже без открытия приложения |
| **Экстренный случай («заменили пару»)** | определяется сервером через `version` в JSON | Приложение сравнивает `version`; при расхождении — обновляет локальную БД |
| **Минимально допустимый интервал вообще** | **10 минут** | Жёсткий пол: чаще — не даёт данных (кэш 5 мин + генерация раз в 15 мин), но повышает риск secondary rate limit |

**Арифметика нагрузки.** 500 студентов × 48 опросов в сутки (каждые 30 минут) =
**24 000 запросов в сутки**. Для raw это ничто (нет счётчика), для Cloudflare
Workers Free (100 000/сутки) — четверть лимита, для GitHub Pages (100 ГБ/мес) —
запас троекратный даже при 200 КБ на файл.

### 6.3. Схема принятия решения в приложении

```
1. Прочитать локальный schedule.json из Room (показать сразу, мгновенно)
2. Если с последней проверки прошло < 10 минут → НЕ ходить в сеть
3. Послать GET с If-None-Match: <сохранённый ETag>
   ├─ 304           → данные актуальны, ничего не делать
   ├─ 200 + новый   → распарсить, записать в БД, сохранить новый ETag
   ├─ 429 / 403     → прочитать Retry-After, назначить отложенный повтор, НЕ ретраить сразу
   └─ ошибка сети   → ничего не менять, показать локальную копию
4. Всегда показывать пользователю поле generated_at из JSON
```

### 6.4. «Храповик» — главный принцип надёжности

Расписание в приложении живёт **локально**. Синхронизация — бонус, а не условие.

- GitHub Actions не запустился → студент видит вчерашнее расписание. **Не «пустой экран».**
- raw заблокирован → пробуем резервный URL (Pages / Cloudflare).
- Все каналы упали → показываем локальную копию + плашку «данные на <дата>».

Именно поэтому в JSON обязательно поле `generated_at`, и именно поэтому в UI нужно
его показывать: студент должен понимать, насколько свежие данные он смотрит.

## 7. Рекомендованная схема

### 7.1. Минимальный вариант (делать сейчас)

Ничего кроме публичного GitHub-репозитория и существующего парсера.

```
GitHub Actions (schedule: "7,22,37,52 * * * *", каждые 15 мин, со сдвигом от :00)
   │
   ├─ парсит сайт колледжа
   ├─ git commit + push только если schedule.json реально изменился
   └─ пишет version + generated_at внутрь JSON
   │
raw.githubusercontent.com/<user>/<repo>/main/schedule.json   ← приложение ходит сюда
   │
ETag + If-None-Match + локальный кэш в Room
```

**Стоимость:** 0 ₽. **Внешние аккаунты:** 1 (GitHub). **Карта:** не нужна.

**Что обязательно сделать в этом варианте:**
- [ ] cron со сдвинутыми минутами (`7,22,37,52`), а не `0,15,30,45`
- [ ] `workflow_dispatch` — кнопка «обновить сейчас» в UI GitHub на случай сбоя cron
- [ ] коммит **только при изменении** содержимого (иначе пустые коммиты)
- [ ] поля `version` и `generated_at` в JSON
- [ ] в приложении: ETag, локальный кэш, интервал ≥ 10 минут, экспоненциальный backoff
- [ ] **держать репозиторий «живым»** (любой коммит/issue раз в 60 дней), иначе
      GitHub **сам выключит** расписание
- [ ] отдельный «технический» GitHub-аккаунт под расписание, не личный

### 7.2. Полный вариант (когда захочется надёжности)

Добавляем к минимальному:

1. **Cloudflare Worker как единая точка входа**
   - проксирует raw, кэширует JSON у себя, отдаёт корректные ETag/304;
   - свой cron каждую минуту (не зависим от капризов `schedule:` GitHub);
   - **умеет ходить в GitHub API с токеном** (5 000/час вместо 60) — токен спрятан
     на сервере, в APK его нет;
   - при недоступности GitHub отдаёт **последнюю известную версию** из своего хранилища.
2. **GitHub Pages как резервный канал** — второй URL в приложении, другой хост.
3. **Внешний планировщик-дублёр** (cron внутри Cloudflare Worker) — дёргает
   `workflow_dispatch` по API, если встроенный `schedule:` GitHub пропустил окно.
4. **Heartbeat-мониторинг** — если расписание не обновлялось > 24 часов, кто-то
   (не GitHub) должен об этом узнать.

**Стоимость:** 0 ₽ (все Free-тарифы). **Внешние аккаунты:** 2 (GitHub + Cloudflare). **Карта:** не нужна.

**Что НЕ надо делать:**
- ❌ jsDelivr `@main` — кэш 12 часов, расписание будет «вчерашним»
- ❌ Просить у приложения commit-SHA через GitHub API — упрёмся в 60/час на один IP
- ❌ Larger runners на GitHub — платно даже в публичном репо
- ❌ Платный тариф Cloudflare ($5/мес) — Free хватает с запасом 100 000 запросов/сутки
- ❌ Класть в публичный JSON имена/данные студентов

## 8. Открытые вопросы к заказчику

1. **Имена преподавателей в публичном JSON.** Расписание колледжа публично, но ФИО
   преподавателей в машиночитаемом виде в публичном репозитории — это персональные
   данные. Публикуем ФИО? Или только фамилию с инициалами? Или ID + локальный справочник?
2. **Данные студентов.** В репозитории есть `students_mpk_full_1703 (2).csv` на 800 КБ.
   **Это в публичный репозиторий попасть не должно ни при каких условиях.** Нужно
   подтверждение, что файл никогда не будет закоммичен (или использовать `.gitignore`
   + отдельный приватный репо).
3. **Насколько критична задержка обновления?** 15 минут опоздания — приемлемо?
   30 минут? Час? От ответа зависит «минимальный» или «полный» вариант (раздел 7).
4. **Нужна ли кнопка «обновить» в приложении?** Если да — она снимает 90 % проблем
   с ненадёжным cron (студент сам обновит, когда видит, что расписание подозрительно старое).
5. **Кто владелец репозитория?** Личный аккаунт разработчика — плохо. Нужен отдельный
   аккаунт или организация колледжа. Кто держит доступ, если разработчик пропадёт?
6. **Резервный канал.** Готов ли заказчик завести второй аккаунт (Cloudflare) ради
   надёжности, или «одного GitHub достаточно»?
7. **Экстренные изменения.** Если пары меняют в 08:00, а cron отработал в 07:52 —
   какая задержка считается недопустимой? Нужен ли ручной «пуш» через
   `workflow_dispatch` как аварийный механизм?
8. **Свой домен.** Нужен ли `schedule.<домен>` (Cloudflare Pages, бесплатно), или
   голая ссылка на GitHub выглядит нормально?
9. **Что показывать, если данные старше N суток?** Какое поведение предпочтительно:
   тихо показывать старое расписание, или показывать предупреждение?

## 10. TL;DR для заказчика

| Вопрос | Ответ |
|---|---|
| Сколько стоит? | **0 ₽.** Везде бесплатные тарифы, карта не нужна |
| Actions бесплатны для публичного репо? | **Да, безлимитно.** Минуты не считаются |
| Как часто можно запускать? | **Минимум раз в 5 минут**, но реально GitHub не гарантирует и этого |
| Насколько опаздывает cron? | **Официально признаны задержки; на практике от 5 минут до 3+ часов, иногда запуск пропадает совсем** |
| Лимит 60/час мешает? | **Нет.** Он про `api.github.com`, а мы читаем `raw.githubusercontent.com` — там счётчика нет |
| Что с кэшем? | **5 минут** на CDN. Для расписания не проблема |
| Как часто приложению опрашивать? | **Не чаще 1 раза в 10–30 минут**, с ETag. Фоном — раз в 12 часов |
| Что если GitHub упадёт/заблокируют? | Приложение показывает **локальную копию**. Синхронизация — бонус, не условие |
| Когда переходить на Cloudflare? | Когда задержка в 30+ минут станет неприемлемой, или когда захочется спрятать токен и получить надёжный планировщик |
